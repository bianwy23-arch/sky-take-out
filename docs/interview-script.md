# 苍穹外卖 - 面试话术文档

## 开场总述（面试官问"介绍一下你的项目"）

> "这个项目是一个外卖平台后端，基础业务包括用户浏览菜品、下单、支付、配送和商家端订单管理。我重点做的不是 CRUD，而是围绕高并发和分布式一致性做了几块改造。最核心的三块是：第一，高并发优惠券抢购，基于 Redis Lua 原子预占、Outbox、MQ、死信有限重放、Redis 回滚和 DB 补偿，异步压测下10万 请求抢 1万 张券零超卖；第二，订单分库分表和分布式 ID，把订单相关表按 user_id 拆成 2 库 8 表，同时把订单 ID 生成从 ShardingSphere 改成应用层 Snowflake + 号段 fallback，解决 ID 回写和时钟回拨问题；第三，限流降级，用 Redis ZSet Lua 滑动窗口做主限流，Redis 异常时按接口风险等级走本地 TokenBucket fallback 或 fail-closed。除此之外，我还做了付费券购买防超卖、订单链路消息一致性、ES 检索和对账、订单超时关闭、UV/PV 统计、下单幂等、WebSocket 推送，以及商家端订单查询的 DB + ES 合并兜底。"

**注意**：说完这段停顿，让面试官选一个方向追问，不要自己一口气全讲完。

## 模块一：高并发抢券防超卖

### 秒杀链路主线

> "我的核心思路是把强一致防超卖放在 Redis，把 DB 侧改成最终一致。用户请求进来以后，先做活动校验，然后通过 Redis Lua 脚本原子完成判重、判断库存、预扣库存和用户占位，这一步保证不会超卖。Lua 成功后，我不会同步直接落 DB，而是先写本地outbox表，再通过定时任务把消息推送到 MQ，由 consumer 异步写 `user_coupon` 成功事实。如果 MQ 消费失败，会进入死信队列做有限次重放；如果重放耗尽，就触发 Redis 回滚补偿，避免 Redis 里占了库存但 DB 永远没成功。同时我还补了 Redis 和 DB 的对账任务，兜底处理少数链路异常。所以整个设计里，Redis 负责防超卖，`user_coupon` 负责记录最终成功事实，MQ 和补偿机制负责把中间异常收敛掉。"

### 【补充追问】为什么要引入 Redis，不能只用 MySQL 吗？

**Q：为什么抢券链路要引入 Redis？只用 MySQL 会出现什么问题？**

> "只用 MySQL 其实也能做抢券，最直接的方案就是在数据库里扣库存，比如执行 `UPDATE coupon SET remaining_count = remaining_count - 1 WHERE id = ? AND remaining_count > 0`，再配合事务和唯一索引处理重复领券。从正确性上说，这套方案可以防超卖，但它的问题是高并发热点场景下性能会很差。"
>
> "因为同一张热门券会把所有请求都打到 `coupon` 表同一行库存上，数据库需要用行锁保护这行数据，结果就是大量并发请求在这一行上排队，吞吐会快速掉下来，数据库容易变成串行瓶颈。"
>
> "另外，像我这个场景是 `100000` 个请求抢 `10000` 张券，实际上有 `90000` 个请求最终只是返回'优惠券已被抢光'。如果没有 Redis，这 `90000` 个失败请求也一样要先打到 MySQL，等于数据库要承担大量无效竞争流量，成本很高。"
>
> "而且抢券不只是扣库存，还要判断用户是否重复领取、记录成功事实、保证幂等。如果这些判断都压在 MySQL 事务里，请求链路会更重，连接占用时间更长，数据库连接池、线程池和行锁竞争都会一起上来。"
>
> "所以我引入 Redis 的核心目的，是把最激烈的竞争前移到内存层。请求先通过 Redis Lua 原子完成判重、判库存、预扣库存和用户占位，让大量失败请求在进入数据库之前就被拦住。这样 DB 不再承担每一次抢券竞争，而是主要负责最终成功事实落库和最终一致性收敛。简单说，只用 MySQL 更像是'能做对，但扛不住热点高并发'；引入 Redis 之后，才能同时兼顾防超卖和吞吐。"

> "这里 DB 落库我后来又做了一层拆分，变成'成功记录落库 + 库存批量聚合刷新'。也就是 consumer 不再逐条去 `update coupon.remaining_count = remaining_count - 1`，而是只插入 `user_coupon` 这条成功领取记录，如果因为重复消息导致 (coupon_id, user_id) 已存在，会抛 DuplicateKeyException。 然后把发生变动的 `couponId` 放进 Redis 脏券集合。后台定时任务每 5 秒扫一次这个脏集合，按券维度执行聚合 SQL，把 `remaining_count` 修正成 `total_count - user_coupon.count(*)`。这样主链路就从'每条消息都更新同一行库存'，改成了'先落成功事实，再按券聚合刷新库存'，把热点行更新和行锁竞争从消费主链路里摘掉了。"聚合刷新库存是定时任务，失败了会定时重新刷新，5s一次



### 三、为什么后来还要继续优化

> "一开始这套链路虽然能保证 0 超卖，但压测后我发现瓶颈会不断后移。最早是 outbox 派发线程里同步等待 confirm/return，导致一轮派发会卡很久，所以我把它改成了 confirm/return callback 异步回写 outbox 状态。后来又发现单线程派发能力不够，我把 outbox 改成多 worker 并行派发。再往后压测时，我发现真正限制吞吐的是 DB 侧逐条更新 `coupon.remaining_count`，因为同一张券会反复更新同一行，形成热点行更新和行锁竞争。所以后来我把库存更新方式改成了方案 2：consumer 只写 `user_coupon` 成功事实，不再逐条扣库存，再通过 Redis 脏集合标记变动券，由定时任务按券聚合刷新 `remaining_count`。这样就把热点更新从主链路里摘掉了。"

**Q：为什么要把脏券放进 Redis？**

> "把脏券放进 Redis，是为了用很低的成本记录'哪些券的库存展示字段失效了，需要重新聚合刷新'。如果 consumer 每次成功都直接更新 `coupon.remaining_count`，热点券会反复竞争同一行数据库库存，形成行锁瓶颈；如果不记脏券，定时任务又只能全量扫描所有券来重算库存，代价太高。"
>
> "所以我用 Redis Set 维护一个脏券集合，consumer 成功写 `user_coupon` 后只做一个 `SADD(couponId)`，后面的任务再按券维度批量刷新库存。这样既避免了主链路热点行更新，也把库存刷新从全量扫描变成了增量处理。"

**Q：`CouponReconcileTask` 的使用场景是什么？**

> "`CouponReconcileTask` 是处理'Redis 有成功占位，但 DB 缺成功事实'的兜底任务。正常链路是 Redis Lua 预占成功后，写 Outbox、投 MQ，再由 consumer 写 `user_coupon` 成功事实；如果这条链路完全正常，对账任务不需要介入。"
>
> "它介入的场景是：Redis 的 `coupon:grabbed:{couponId}` 里已经有这个 `userId`，说明系统已经给用户占住了抢券资格；但 MQ、consumer 或 DB 落库链路某个环节异常，导致 DB 的 `user_coupon` 没有对应记录。这时如果不补，Redis 认为用户抢到了，DB 却没有最终成功事实，系统状态就不一致。"
>
> "所以它每 5 分钟用 `SCAN` 扫 `coupon:grabbed:*`，逐个检查 `(couponId, userId)` 是否已经存在于 DB。如果 DB 缺记录，就优先补写 `user_coupon` 来收敛一致性；但如果这条记录已经进入 Redis 回滚补偿，就跳过，避免把失败链路误补成成功。"

对账补偿的场景：

1.Redis Lua 成功，Outbox 写成功**

   \- 请求已进入可靠链路

   \- 前端收到“已受理”

2. **Outbox 投递 MQ 成功，但消费者一直失败**

   \- 比如消费者处理异常、DB 短暂抖动、服务重启

   \- 但还没走到“死信重放耗尽并判定失败”

3. **MQ 消费成功前服务异常中断**

   \- 消息可能被重投

   \- 在某些极端情况下，DB 记录还没写成



### 【第二层追问】失败补偿边界

**Q：什么场景回滚 Redis，什么场景补偿 DB？**

> "边界是看这次 Redis 预占有没有进入可靠消息链路。如果 Redis 成功，但 Outbox 最终写不进去，说明后面没有 MQ、没有消费者、没有可靠重试，这时必须回滚 Redis。"
>
> "如果 Outbox 已经写入，消息后续投递失败或消费失败，就不能马上回滚 Redis，因为消息还有机会通过重试恢复。这时先让 Outbox 或死信重放继续推进 DB。只有死信有限次重放耗尽，确认不可恢复，才回滚 Redis。"
>
> "反过来，如果 Redis 里有用户占位，但 DB 缺少 `user_coupon`，说明消息链路可能漏落库，这时对账任务补偿 DB，而不是回滚 Redis。简单说：消息没进可靠链路，回滚 Redis；消息进了可靠链路，优先补 DB；最终死信失败，才回滚 Redis。"

**Q：死信回滚会不会造成库存虚增？**

> "不会，因为死信回滚必须做幂等校验。回滚 Lua 只在 Redis Set 里还存在这个 userId 时才执行 `SREM` 和库存加 1；如果已经被回滚过，第二次执行发现 userId 不在 Set 里，就不再加库存。这样重复死信、重复调度都不会把库存加多。"



### 【补充追问】老方案行锁证据与新方案压测结果

**Q：你怎么证明老方案有行锁竞争？优化后效果怎么验证？**

> "老方案里，MQ 消费者每消费一条抢券消息，就直接执行 DB 扣库存：`UPDATE coupon SET remaining_count = remaining_count - 1 WHERE id = ? AND remaining_count > 0`。这个方案虽然能依赖 MySQL 行锁避免超卖，但热点券场景下，所有消费者都会竞争 `coupon` 表同一行库存，DB 会变成串行瓶颈。为了验证这个问题，我做过行锁复现实验：用 50 个并发 worker 同时执行这条扣库存 SQL，并用 `performance_schema.data_lock_waits` 每 0.2 秒采样。结果采样期间捕捉到 `lockWaitNonEmptyLines=57378`，去重后有 `unique waiting transactions=50`，锁类型全部是 `sky_order_0.coupon.PRIMARY.RECORD.X,REC_NOT_GAP.WAITING`。直接证据里能看到 `OBJECT_NAME=coupon`、`INDEX_NAME=PRIMARY`、`LOCK_TYPE=RECORD`、`LOCK_MODE=X,REC_NOT_GAP`、`LOCK_STATUS=WAITING`，而且 `waiting_sql` 正是这条库存扣减 SQL。这说明旧方案不是理论上可能有锁，而是实际能观察到热点库存行上的排他记录锁等待。"
>
> "优化后我把库存事实前移到 Redis，用 Lua 脚本原子完成用户判重、库存判断、`DECR` 扣库存和 `SADD` 记录已抢用户。Redis 预扣成功后，通过 Outbox/MQ 异步写 `user_coupon` 成功事实，DB 的 `coupon.remaining_count` 不再每条消息直接扣减，而是后续按 `user_coupon` 聚合刷新。这个改造的核心是把高并发库存竞争从 MySQL 单行热点更新里移出来。"
>
> "我后面又做了一轮更贴近真实连接模型的异步压测。压测工具不是 JMeter 线程模型，而是 Python `asyncio + aiohttp`，使用长连接和连接池，避免每个请求都新建 TCP 连接，把压测重点放在抢券业务链路本身。测试场景是 10 万个不同用户，每个用户只请求一次，抢 1 万张券；压测参数是 `concurrency=1000`，也就是最多同时维持 1000 个异步请求在飞，`ramp=5s`，表示 5 秒内快速拉满并发。这不是 10 万并发，而是 10 万总请求量、1000 异步并发。"
>
> "这轮结果是：总请求 `100000`，HTTP 成功 `100000`，错误率 `0%`，总耗时 `19.39s`，吞吐大约 `5156.93 QPS`，平均响应时间 `191.39ms`，P95 是 `504.17ms`，P99 是 `841.39ms`。业务结果上，刚好 `10000` 个用户抢券成功，剩下 `90000` 个返回'优惠券已被抢光'。"
>
> "压测后我又做了 Redis 和 DB 的一致性校验：Redis 里的 `coupon:stock` 是 `0`，`coupon:grabbed` 集合大小是 `10000`；DB 里的 `user_coupon` 记录数是 `10000`，去重用户数也是 `10000`，`coupon.remaining_count` 是 `0`。所以这轮验证了三个结论：第一，1000 异步并发、5 秒快速放量下系统可以稳定响应；第二，Redis Lua 预扣没有超卖；第三，异步落库后 Redis 和 DB 最终一致。"

**Q：5156 QPS 为什么不是 2 秒完成？P99 是什么时间？**

> "这里的 `5156 QPS` 指的是系统平均每秒完成的 HTTP 请求数，不是每秒成功发券数。这轮压测总请求量是 `100000`，其中 `10000` 个请求抢券成功，剩下 `90000` 个请求返回'优惠券已被抢光'。所以总耗时应该按总 HTTP 请求量算：`100000 / 5156 ≈ 19.39s`，这和实际压测耗时 `19.39s` 是一致的。如果只用库存数 `10000 / 5156` 算出 2 秒，那其实算的是成功发券数，不是接口总处理量。"
>
> "另外，这里的 `P99=841ms` 是抢券 HTTP 接口的响应时间 P99，也就是压测脚本从发起 `POST /user/coupon/grab/{couponId}` 到收到 HTTP 响应的耗时。它包含客户端连接池开销、Spring Boot 接收请求、活动校验、Redis Lua 判重/判库存/预扣库存、写 Outbox 和返回响应；但不包含后续 MQ consumer 写 `user_coupon`、DB 聚合刷新 `remaining_count` 这些异步落库链路。后面的异步链路我是通过 Redis 和 DB 最终一致性校验来验证的。"

**Q：为什么不用单机 JMeter 直接压 10 万用户？JMeter 压测上限怎么解释？**

> "这里我会专门区分 JMeter 线程压测和异步压测。单机 JMeter 不适合直接模拟 10 万用户同时抢券，因为 JMeter 常规模型基本是一个虚拟用户对应一个 Java 线程。单机拉到几千、上万线程时，我实际遇到过 `pthread_create failed (EAGAIN)`、`Failed to start native thread`、`Too many open files`、`ConnectTimeoutException` 这些问题，这些先打到的是压测端线程、文件描述符、socket 和本机网络栈上限，不一定是服务端业务逻辑上限。尤其本地环境里 JMeter、Spring Boot、MySQL、Redis、RabbitMQ 都在同一台机器上，还会互相抢 CPU、内存和端口资源。"
>
> "所以如果面试官问 10 万用户怎么模拟，我会说严格模拟需要分布式 JMeter 或异步压测工具。本地我最后采用异步压测，是用少量线程加事件循环管理大量非阻塞连接，并且用 10 万个不同 token，每个用户只请求 1 次。这个模型比 `2000×50` 这种重复 loop 更贴近真实抢券业务，也避免了单机 JMeter 线程数先成为瓶颈。"

### 【补充追问】开发过程中遇到的困难

**Q：这个功能开发过程中，最大的困难是什么？**

> "我开发过程中遇到的最大困难，其实不是把抢券功能做出来，而是把它做成'高并发下不超卖、失败可补偿、而且异步链路能真正跑得动'。这个模块我前后踩了三类问题：第一类是怎么保证 0 超卖；第二类是 Redis、MQ、DB 之间怎么收敛到最终一致；第三类是压测后发现瓶颈会不断后移，需要持续定位和优化。"

**Q：第一类困难，怎么保证 0 超卖？**

> "一开始最难的是，抢券这种场景不能让多个请求同时扣到同一份库存。我最早考虑过数据库锁或者分布式锁，但后来发现这个竞争逻辑其实都在 Redis 里：判重、判断库存、扣库存、记录用户占位，都可以放到一个 Lua 脚本里做。所以我最后用 Redis Lua 把这几个步骤原子化了，把超卖问题前置解决。这个过程其实体现的是，我不是随便套一个分布式锁方案，而是比较过 DB 锁、Redis 锁和 Lua 之后，选了更适合这个场景的做法。"

**Q：第二类困难，Redis 成功了，但 DB 没成功怎么办？**

> "第二个困难是链路一致性。Redis 预占成功只能说明'先把资格占住了'，但不能代表最终成功，因为后面还有 Outbox、MQ、consumer、DB 落库。如果 Redis 成功后直接返回成功，一旦 MQ 或 DB 某个环节失败，就会出现 Redis 认为抢到了、DB 却没有成功记录的问题。"
>
> "所以我后来把链路改成：Redis Lua 成功后先写 Outbox，再异步发 MQ，由 consumer 落 `user_coupon` 成功事实。如果消息失败，不是立刻回滚 Redis，而是先进死信队列做有限次重放；只有重放耗尽了，才做 Redis 回滚。如果回滚也失败，就进入补偿表和后台补偿任务。除此之外，我还补了 Redis 和 DB 的对账任务，用来兜底 Redis 已占位但 DB 漏落库的边界场景。这个问题最难的地方，不是某一个技术点，而是要把失败边界和补偿边界全部理清楚。"

**Q：第三类困难，为什么后来还要继续优化？**

> ###### "第三个困难是，我一开始以为只要保证 0 超卖就够了，结果压测后发现不是这样。最早接口 RT 看起来不差，但压测结束时 DB 落库严重落后，说明问题不在前面的 HTTP 接口，而在异步成功链路。后来我一轮轮压测，发现瓶颈是不断后移的。"
>
> "最早是 Outbox 派发线程里同步等待 confirm/return，导致一轮派发会卡很久，所以我把它改成了 callback 异步回写 Outbox 状态。
>
> 后来又发现单线程派发能力不够，我把 Outbox 改成多 worker 并行派发。
>
> 再往后压测时，我发现真正限制吞吐的是 DB 侧逐条更新 `coupon.remaining_count`，因为同一张券会反复更新同一行，形成热点行更新和行锁竞争。所以后来我把库存更新方式改成了方案 2：consumer 只写 `user_coupon` 成功事实，不再逐条扣库存，再通过 Redis 脏集合标记变动券，由定时任务按券聚合刷新 `remaining_count`。
>
> 这样就把热点更新从主链路里摘掉了。"聚合刷新库存是定时任务，失败了会定时重新刷新，5s一次

**Q：DB 侧库存怎么保证不小于 0？**

> "我这里不是直接在 DB 里逐条 `remaining_count - 1` 扣库存，而是把抢券库存拆成了两层。"
>
> "第一层在 Redis。抢券请求进入后，会执行 Lua 脚本，把'判断是否重复领取、判断库存是否大于 0、扣减库存、记录用户已领取'放在一个原子脚本里完成。核心逻辑是先 `GET` 库存，如果 `stock == nil or stock <= 0` 就直接返回库存不足，只有库存大于 0 才执行 `DECR`，然后 `SADD` 记录用户已领取。因为 Lua 在 Redis 中是原子执行的，所以不会出现多个线程同时看到库存为 1，然后都扣成功，导致 Redis 库存变成负数的问题。"
>
> "第二层在 DB。DB 不走每条 MQ 消息都 `remaining_count - 1` 的方式，因为热点券会打到同一行，行锁竞争很重。消费者只插入一条成功领取事实到 `user_coupon`，并依赖 `(user_id, coupon_id)` 唯一索引保证同一用户不会重复领取。然后把 `couponId` 放进 Redis 脏券集合，定时任务按券维度聚合刷新库存：`UPDATE coupon c SET c.remaining_count = GREATEST(0, c.total_count - (SELECT COUNT(*) FROM user_coupon uc WHERE uc.coupon_id = c.id)) WHERE c.id = ?`。这里 `GREATEST(0, ...)` 是最后一层防御，保证即使出现历史脏数据或人工补数异常，DB 的剩余库存展示字段也不会小于 0。"
>
**小结：防库存小于 0 的三层保障**

> "所以防库存小于 0 分三层：第一，Redis Lua 原子判断库存大于 0 才扣减；第二，`user_coupon` 唯一索引保证成功事实不重复；第三，DB 派生库存用 `GREATEST(0, ...)` 兜底，避免异常脏数据把展示库存刷成负数。真正防超卖靠 Redis Lua，DB 的 `GREATEST` 是最后一层展示字段保护。"

## 模块二：分库分表与分布式 ID

### 【主动讲解】30 秒话术

> "订单这块我做了两件事。第一是分库分表，用 ShardingSphere-JDBC 按 `user_id` 把订单相关表拆成 2 个库、每库 8 张表，共 16 个分片，用户侧订单查询能按 userId 精确路由。第二是分布式 ID，把订单主键从 ShardingSphere 内置 Snowflake 改成应用层 `Snowflake + 号段 fallback`。正常情况下应用生成订单 ID 并写回实体；检测到时钟回拨时切到号段模式，时钟恢复后再切回 Snowflake。"

---

### 【第一层追问】分片策略

**Q：为什么用 user_id 做分片键，不用 order_id？**

> "主要从查询场景考虑。用户端最高频的是'查我的订单'和'订单详情'，请求天然带 userId。用 userId 分片，同一个用户的订单、订单明细、支付流水和 Outbox 记录可以落到同一个分片，查询和事务都更简单。如果用 orderId 分片，用户查订单列表就要广播 16 张表再合并，反而不适合主链路。"

**Q：商家端查询没有 userId，怎么处理？**

> "商家端确实不是天然带分片键，所以不能简单说所有查询都精准路由。我做的是分层处理：近期订单用 DB 查询兜底，保证新订单商家能尽快看到；历史和大范围模糊查询主要走 ES，降低跨分片广播压力。当前实现里管理端订单条件查询会把近 70 分钟 DB 结果和 ES 结果合并去重，DB 结果优先，解决 ES 异步延迟导致的新订单不可见问题。"

---

### 【第二层追问】Snowflake + 号段 fallback

**Q：为什么要从 ShardingSphere Snowflake 改成应用层生成？**

> "一开始用 ShardingSphere 的 Snowflake，坑是 ID 在 ShardingSphere 改写 SQL 时生成，MyBatis 实体拿不到回写后的 id。订单明细和 Outbox 都需要 orderId，实体 id 为 null 会影响后续链路。改成应用层生成后，`orders.setId(orderIdGenerator.nextId())` 先执行，后面的订单明细、支付流水、Outbox 都能直接使用同一个 orderId，不需要插入后再回查。"

**Q：Snowflake 时钟回拨怎么办？**

> "纯 Snowflake 最怕时钟回拨，因为时间戳倒退可能和之前的时间片生成重复 ID。我选的是 Snowflake + 号段 fallback：正常情况下走 Snowflake；如果检测到当前时间小于上次发号时间，不阻塞等待，也不直接报错，而是切到数据库号段模式，从 `id_segment` 表批量拿一段 ID 在内存里发。后台持续观察系统时间，时间恢复到安全区间后再切回 Snowflake。"
>
> "这个方案的取舍是：常态下 Snowflake 性能高、趋势递增；异常时号段模式保证服务不断和 ID 不重复。号段起始区间和 Snowflake 区间做隔离，避免两套 ID 空间碰撞。"

**Q：你能把整个切换流程再讲一遍吗？**

> "可以。下单时先调用 `OrderIdGenerator.nextId()`，把生成的 ID 直接写回 `orders.id`，后面的订单明细、支付流水、Outbox 都直接用这个 ID。正常情况下走 Snowflake，`workerId` 配的是 1，机器号 10 位，序列号 12 位，所以单机每毫秒最多 4096 个 ID。"
>
> "如果检测到时钟回拨，我分两种情况：回拨不超过 5ms，就短暂等待系统时间追上来，继续走 Snowflake；如果回拨超过 5ms，就切到号段模式。号段模式下从 `id_segment` 表按 `orders` 这个业务类型申请一段 ID，当前初始化是从 `1000000000000000` 开始，每次申请 1000 个，应用就在内存里发这一段。"
>
> "进入号段模式后，不会立刻切回 Snowflake，而是持续观察时间。等系统时间恢复稳定、并且已经比上一次 Snowflake 时间戳往后超过 30 秒，再自动切回 Snowflake。整个策略就是：正常走 Snowflake，小回拨等待，大回拨切号段，时间稳定后自动恢复。"

**Q：还需要插入后回查订单 ID 吗？**

> "不需要。现在主键是在应用层生成后显式写进实体和 insert SQL 的，插入前 `orders.getId()` 就已经有值。插入后回查是旧方案为了弥补 ShardingSphere ID 不回写的问题，现在这个问题已经从根上绕开了。"

### 【第三层追问】扩展问题

**Q：数据继续增长，16 个分片不够了怎么扩容？**

> "这是分库分表最头疼的问题。一般有两种思路：一是提前规划好足够多的虚拟分片，扩容时只做数据迁移不改路由规则；二是用一致性哈希，扩容时只需迁移少量数据。不过说实话，这个项目规模还没到需要扩容的地步，我只是了解方案，没有实际做过。"

## 模块三：Redis ZSet 滑动窗口限流

### 【主动讲解】30 秒话术

> "限流我做的是 Redis 主限流 + 本地 fallback + 降级开关。Redis 正常时，用 ZSet + Lua 实现滑动窗口，每个 key 记录窗口内请求时间，Lua 原子完成清理过期数据、统计数量、判断阈值和写入本次请求。Redis 异常时不是简单放行，而是按接口风险等级处理：抢券接口 fail-closed；下单、登录走本地严格 TokenBucket；普通查询走本地宽松 TokenBucket。连续 Redis 异常会进入降级状态，短时间内直接走本地策略，后台健康探测恢复后再切回 Redis。"key：限流桶本身，比如 rate:user:123:/user/order/submit
>
>  \- score：请求时间戳，毫秒级，用来判断是否落在滑动窗口内
>
>  \- member：本次请求的唯一标识，防止同一毫秒并发覆盖

---

### 【第一层追问】为什么用滑动窗口

**Q：为什么用 ZSet 实现滑动窗口，不直接用 INCR 计数？**

> "INCR 是固定窗口计数，会有临界突刺。比如用户在第 59 秒打 30 次，第 61 秒又打 30 次，两个固定窗口都没超，但实际 2 秒内打了 60 次。ZSet 滑动窗口每次都以当前时间往前推 60 秒，统计的是连续时间窗口，能避免这种边界问题。"

**Q：为什么用 Lua 脚本？**

> "限流逻辑是'删旧记录、查数量、判断、写新记录'，必须原子执行。如果拆成多次 Redis 命令，并发下多个请求可能同时读到 count 没超，然后都写入，实际就突破阈值。Lua 在 Redis 单线程里执行，中间不会被其他请求打断。"

**Q：ZSet member 为什么不能直接用毫秒时间戳？**

> "同一毫秒内可能有多个请求，如果 member 都用同一个时间戳，ZSet 会覆盖旧 member，导致计数偏小。现在 member 用 `时间戳 + 线程 id + UUID` 保证唯一，score 仍然用毫秒时间戳做窗口判断。"

---

### 【第二层追问】Redis 异常兜底

**Q：Redis 挂了为什么不能直接放行？**

> "普通查询短暂放行问题不大，但抢券、下单、登录这类接口遇到恶意请求或爬虫时，Redis 挂了如果完全放行，相当于限流失效，压力会直接打到业务和数据库。所以我按风险等级降级：抢券是最高风险，Redis 限流不可用就直接拒绝；下单和登录走本地严格限流；普通查询走本地宽松限流。"

**Q：本地 fallback limiter 是什么？**

> "本地 fallback 是进程内的轻量 TokenBucket。每个限流 key 对应一个桶，桶有容量和补充速率；请求来了先按时间补令牌，有令牌就扣 1 个放行，没有令牌就拒绝。Caffeine 负责管理这些桶的生命周期，限制最大 key 数量，并让长时间不用的桶自动过期，避免内存无限增长。"

**Q：连续 Redis 异常怎么处理？**

> "不是每次请求都傻等 Redis 超时。拦截器统计连续失败次数，达到阈值后进入降级状态，比如 30 秒内直接跳过 Redis，按本地策略处理，避免每个请求都阻塞在 Redis 超时上。后台每 5 秒做一次 Redis `PING`，连续成功几次后退出降级，恢复 Redis 主限流。"

---

### 【补充追问】严格令牌桶、宽松令牌桶和降级流程

**Q：严格令牌桶、宽松令牌桶和降级流程具体怎么讲？**

> "可以按正常路径、异常路径、降级恢复三段讲。正常路径是 Redis 主限流，所有 `/user/**` 请求先走 Redis ZSet Lua 滑动窗口。当前参数是 60 秒最多 30 次，Lua 原子执行清理窗口外数据、统计窗口内数量、超过阈值返回 429、没超过就写入本次请求。"
>
> "异常路径是 Redis 短暂失败时的 fallback。我把接口分成三个风险等级：抢券是 `CRITICAL`，下单、支付、登录是 `HIGH`，普通用户查询是 `LOW`。Redis 异常时，抢券直接 fail-closed，因为这是高风险入口，限流不可用时继续放行容易被打穿；下单、支付、登录走本地严格令牌桶，当前是每个 key 每分钟 5 个令牌；普通查询走本地宽松令牌桶，当前是每分钟 60 个令牌。"
>
> "本地令牌桶是进程内兜底，不是替代 Redis 主限流。每个限流 key 对应一个桶，请求来了先按时间补令牌，有令牌就扣 1 个放行，没有令牌就返回 429。桶对象用 Caffeine 管理，最多 10 万个 key，10 分钟没有访问自动过期，避免 Redis 故障期间本地内存无限增长。"
>
> "降级恢复是处理 Redis 连续异常。当前阈值是连续失败 5 次，进入降级后持续 30 秒；这 30 秒内请求不会每次都等 Redis 超时，而是直接走本地策略。后台每 5 秒探测一次 Redis，连续 3 次 `PING` 成功后退出降级，恢复 Redis 主限流。总结就是：Redis 正常走分布式滑动窗口，Redis 抖动走本地令牌桶，Redis 连续异常打开降级开关，恢复稳定后自动切回 Redis。"

---

### 【第三层追问】限流 key 与风险等级

**Q：为什么要区分 IP、userId、登录标识？**

> "不同接口能拿到的身份信息不一样。登录前没有 userId，只能按 IP 或登录标识限流；登录后用户接口可以按 userId + URI 限流，更精准；如果只按 IP，家庭、公司、校园网这种 NAT 场景会误伤一批用户；如果只按 userId，登录接口又覆盖不到。所以 key 要按接口阶段和风险来设计。"

**Q：这个方案和 Sentinel 比有什么取舍？**

> "Sentinel 能做更完整的流控、熔断、热点参数和控制台规则管理，但引入成本更高。这个项目的目标是把核心接口在 Redis 正常和异常时都保护住，所以用 Redis Lua + 本地 TokenBucket 足够轻量，也方便解释。真到生产复杂治理，可以再接 Sentinel 或网关层限流。"

---

## 模块四：四层数据一致性

### 【主动讲解】30 秒话术

> "我设计了四层一致性方案。第一层是库存，下单和扣库存在同一个数据库事务里，强一致，失败直接回滚防止超卖。第二层是订单状态变更和消息发布，用 Outbox 模式保证最终一致，业务写库和写 Outbox 在同一事务，Scheduler 轮询发 MQ，消息不丢。第三层是物流事件，外部物流系统通过回调通知状态变化，我通过 MQ 异步消费，用状态机校验防止非法跳转，配送取消时用乐观锁恢复库存。第四层是 ES 索引同步加定时对账兜底，最坏情况一小时自动修复不一致。"

### 【主动讲解】2 分钟口语版

> "我这个项目把订单一致性拆成四层，不是追求全链路强一致，而是按风险分级治理。"
>
> "第一层是库存强一致。下单时'订单落库、明细落库、库存扣减'在同一个本地事务里完成，任何一步失败都回滚，所以不会超卖。这层解决的是核心资金和库存安全问题。"
>
> "第二层是消息最终一致。订单状态变化后，我不在事务里直接发 MQ，而是把业务变更和 Outbox 消息表一起提交。这样即使 MQ 当时不可用，消息也不会丢。后面由调度任务扫描 Outbox 再投递 MQ，失败按重试策略处理。"
>
> "第三层是消费端幂等一致。MQ 是至少一次投递，可能重复，所以消费者先写 `order_event_consume_log`，靠 `(consumer_name, event_id)` 唯一键去重。插入成功才继续执行业务，比如同步 ES；如果唯一键冲突，说明这条消息处理过，直接跳过，避免重复副作用。"
>
> "第四层是 ES 对账兜底。ES 同步是异步链路，可能延迟或失败。我在消费失败时抛异常让 MQ 重试，同时做定时对账任务，按时间窗比对 MySQL 和 ES 差异并修复，保证最终收敛。"
>
> "所以整体思路是：核心数据本地强一致，跨系统用 Outbox + MQ 做最终一致，消费端幂等防重，最后再用对账兜底。这样比上分布式事务更轻，性能和复杂度更可控，也覆盖了消息丢失、重复消费、索引延迟这几类典型故障。"

---

### 【第一层追问】Outbox 模式原理

**Q：Outbox 模式和直接发 MQ 有什么区别？**

> "直接发 MQ 有一个经典问题：业务写库成功了，但发 MQ 失败了（网络抖动、MQ 宕机），下游就收不到消息，数据不一致。反过来也有问题：先发 MQ 成功了，但写库失败了，下游收到了一条不该存在的消息。"
>
> "Outbox 模式的核心思路是把'写库'和'写消息'合并成一个数据库事务。业务数据和 Outbox 消息表在同一个事务里提交，要么都成功要么都回滚。然后独立的 Scheduler 轮询 Outbox 表，把待发送的消息投递到 MQ。这样即使 MQ 短暂不可用，消息也不会丢，Scheduler 会重试。"

**Q：你的 Outbox 表结构是什么样的？**

> "主要字段有：id、分片键 user_id、事件类型（如 ORDER_CREATED）、消息内容、状态（待发送/已发送）、下次重试时间、重试次数。Scheduler 每隔几秒查一批 status=0 且 next_retry_time <= now() 的记录，发送成功后更新状态。"

---

### 【第二层追问】幂等与重复

**Q：消息重复投递怎么办？怎么保证幂等？**

> "Outbox 模式保证的是'至少投递一次'，确实可能重复。Consumer 端需要做幂等。我们用了消费日志表（consume_log），每条消息有唯一的 messageId，Consumer 处理前先查 consume_log，已经处理过的直接跳过。insert consume_log 和业务操作在同一事务内，保证不会重复处理。"

**Q：Scheduler 轮询有性能瓶颈吗？**

> "目前每 5 秒轮询一次，每次最多取 100 条，对于当前体量足够。如果消息量大了，可以考虑两个优化：一是分片轮询，不同 Scheduler 实例负责不同分片的 Outbox；二是用数据库的 binlog 监听（比如 Canal）替代轮询，变被动为主动推送。"

**Q：你简历里写了'为 Outbox 派发、补偿对账和通知任务设计独立异步线程池'，这块具体怎么讲？**

> "这块本质上是在做后台任务隔离。项目里有几类典型的异步任务：Outbox 定时派发、ES 定时对账修复、订单状态 WebSocket 通知。它们都不是用户请求线程里的强实时逻辑，但都有可能比较耗时。如果直接混用 Spring 默认线程池，后台任务一旦堆积，就容易和其他异步逻辑互相影响。"
>
> "所以我单独配了一个异步线程池，核心参数是 core=8、max=16、queue=500，专门承接这几类后台任务。拒绝策略我没有直接丢任务，而是先打一条线程池状态日志，再走 `CallerRunsPolicy` 做反压，避免消息或补偿任务无声丢失。"
>
> "另外我在线程池层统一补了三件事：第一是异常处理，异步方法没 catch 住的异常会统一打到日志里；第二是慢任务日志，用 `TaskDecorator` 记录执行耗时，超过 1 秒就告警；第三是每分钟跑一次线程池巡检，输出 active、queueSize、completedTaskCount 这些指标，繁忙时打 WARN。任务本身再用 `AtomicBoolean` 防止上一轮还没结束，下一轮定时任务又并发进来。这样后台链路的隔离性和可观测性会好很多。"

**Q：为什么要单独线程池，直接用默认的 `@Async` 不行吗？**

> "能跑，但不利于治理。默认线程池一般是全局共享的，今天 Outbox 重试堆积，明天 ES 对账跑慢，后天通知任务一多，几类任务会互相抢线程，问题一出来很难定位。单独线程池的好处是边界清楚：主业务线程和后台补偿线程分开，容量、日志、监控都能单独看，出了问题也能快速判断到底是派发堆积、对账变慢，还是通知链路有异常。"

**Q：线程池参数是怎么设置的？为什么这么配？**

> "这个线程池的核心参数是 core=8、max=16、queue=500、keepAlive=60s，线程名前缀是 `sky-async-`。它主要承接 Outbox 派发、ES 对账修复、订单状态通知这类后台异步任务，任务类型偏 I/O 型，偶尔会因为 MQ、ES、WebSocket 连接波动出现耗时抖动。"
>
> "我的思路是先保证常态吞吐，再给短时突发留余量。8 个核心线程用于常态处理，16 个最大线程相当于给突发场景一倍扩容空间；队列 500 用来削峰，避免一有波动就疯狂创建线程；空闲线程 60 秒回收，避免高峰过去后资源一直占着。"
>
> "这个参数不是说永远最优，而是一个保守起点。后续要看运行指标调：如果 active 长期接近 16、queueSize 持续上涨，说明池子或下游处理能力不够；如果线程数很低但单个任务耗时很长，就要先查慢任务日志，看是 ES 对账慢、MQ 派发慢，还是通知链路阻塞。"

**Q：拒绝策略为什么选 `CallerRunsPolicy`，不直接丢弃？**

> "这几类任务都不适合静默丢弃。Outbox 派发丢了可能导致下游收不到消息，对账补偿丢了会延长不一致时间，通知任务丢了用户体验会变差。所以我选 `CallerRunsPolicy` 做反压，让提交方自己执行，相当于在高峰期主动降速，至少保证任务不丢。同时我会把 active、queueSize、completedTaskCount 这些状态打出来，方便判断是不是容量要扩。"

**Q：慢任务日志和周期监控分别解决什么问题？**

> "慢任务日志解决的是单次任务级别的问题，比如某次 ES 对账突然跑了 3 秒、某次通知阻塞了很久，我能直接从日志里看到 taskId、耗时和线程名。周期监控解决的是线程池整体水位问题，比如 active 长期接近 max、queueSize 持续积压，这说明不是偶发慢，而是池子整体吃紧了。一个看单点慢调用，一个看整体容量趋势，两者结合更容易定位问题。"

### 【第三层追问】物流事件一致性

**Q：物流状态变更是怎么处理的？**

> "外部物流系统状态变化后通过 HTTP 回调通知我们，Controller 收到通知后不直接写库，而是发一条消息到 RabbitMQ。下游的 LogisticsStatusMqConsumer 消费这条消息，做四件事：第一，写消费日志表做幂等去重，event_id 有唯一索引，重复投递直接跳过；第二，用状态机校验当前订单状态能不能转移到目标状态，比如'待接单'只能到'已接单'，不能直接跳到'已完成'，防止乱序消息破坏数据；第三，更新分片库里的订单状态，带上 userId 分片键精准路由；第四，同步更新 ES 索引。"

**Q：配送失败取消时库存怎么恢复？不会并发冲突吗？**

> "支付成功后库存已经真实扣减了，配送失败取消需要把库存加回去。这里用了乐观锁，dish 表有一个 version 字段，更新时 WHERE version = #{version}，如果被别人改过就 rows=0，然后重新读最新版本再试，最多重试 3 次。相比悲观锁（SELECT FOR UPDATE），乐观锁在低冲突场景下不需要加锁等待，性能更好。3 次重试还失败就记错误日志，人工介入处理。"

**Q：为什么物流通知要走 MQ，不直接在 Controller 里处理？**

> "两个原因。第一，物流回调是外部系统发来的，响应要快，不能在回调接口里做一堆数据库操作，否则超时对方会重试，造成重复通知。走 MQ 之后 Controller 只管发消息，毫秒级返回。第二，MQ 天然提供了重试机制，Consumer 处理失败消息会重新入队，不需要自己写重试逻辑。"

**Q：你这套物流回调到落库的代码链路怎么讲？**

> "可以按四步讲。第一步是回调入口：`LogisticsNotifyController#statusMock`（本地联调 mock）接收 `orderNo/logisticsStatus/eventId`，组装 JSON 后调用 `LogisticsEventMqPublisher.publish`。第二步是消息投递：`LogisticsEventMqPublisher` 用 `RabbitTemplate.convertAndSend(exchange, routingKey, payload)` 发到物流状态队列。第三步是异步消费：`LogisticsStatusMqConsumer#consume` 监听物流队列，先写 `logistics_event_consume_log` 做幂等去重，再做状态机校验，校验通过后更新订单状态。第四步是下游同步：消费成功后同步 ES 状态，并通过 WebSocket 推送用户端订单状态变化。"
>
> "如果面试官继续追问，我会补一句：生产场景这个 Controller 应该接真实外部物流回调；当前项目保留了 mock 入口是为了本地联调和压测可复现。"

---

### 【第四层追问】方案对比

**Q：为什么不用 Seata 这种分布式事务框架？**

> "Seata 需要引入 TC（事务协调者）组件，增加了运维复杂度和网络开销。而且 Seata 的 AT 模式需要对每张表加 undo_log，对分库分表场景的兼容性也有问题。我们的场景不需要强一致的分布式事务，最终一致就够了，Outbox 模式更轻量，只依赖本地数据库事务，没有额外组件。"

**Q：库存扣减为什么不用 Redis 预扣？**

> "Redis 预扣适合秒杀场景，需要处理 Redis 和数据库的双写一致性问题。我们是普通外卖下单，并发没有到秒杀级别，数据库事务内直接扣减就够了，方案更简单可靠。如果后面有秒杀需求，可以加 Redis 预扣 + 异步落库。"

## 模块五：Elasticsearch 商品搜索

### 【主动讲解】30 秒话术

> "我接入 Elasticsearch 做菜品全文检索，用 IK 分词器支持中文分词。写入端还是走 MySQL，数据通过 MQ Consumer 异步同步到 ES，查询端走 ES，实现读写分离。这样用户搜索'宫保鸡丁'能匹配到'宫保'和'鸡丁'，MySQL 的 LIKE 做不到这种语义分词。"

### 【主动讲解】2 分钟口语版

> "我在项目里把 ES 用在两块：菜品全文检索和管理端订单条件检索。菜品这块，C 端搜索接口是 `/user/dish/search`，查 `sky_dishes` 索引；`name`、`description` 用 IK 分词，查询时做 `multiMatch`，并且强制过滤 `status=ENABLE`，保证只返回起售菜品。订单这块，管理端历史订单和大范围模糊查询主要走 `sky_orders` 索引，支持按订单号、手机号、状态、时间区间组合过滤，减少数据库复杂条件查询压力。"
>
> "这里有一个细节：ES 是近实时和最终一致的，新订单刚下完可能还没同步到 ES，商家端立刻查会看不到。所以管理端订单查询不是纯 ES，而是把近 70 分钟 DB 查询结果和 ES 查询结果合并去重，DB 结果优先。这样新订单走 DB 保证可见，历史和模糊查询继续利用 ES 的性能。"
>
> "数据同步我做了三层保障。第一层是业务实时双写：菜品增删改、订单状态变更时，Service 层同步写 ES。第二层是 MQ 异步同步：订单事件通过 Outbox -> MQ -> Consumer 再写 ES，避免漏更新。第三层是定时对账兜底：`EsReconcileTask` 每小时跑一次，菜品全量对账，订单对账近 24 小时，发现缺失或状态不一致就自动修复。"
>
> "这套设计的取舍是：不追求 ES 强一致，优先保证主业务可用性，再用 MQ 重试 + 对账任务实现最终一致。可以一句话总结：ES 负责'查得快'，MySQL 负责'写得准'，一致性靠异步和补偿闭环。"

### 【第一层追问】倒排索引原理

**Q：ES 为什么查得快？倒排索引是什么？**

> "正排索引是文档 → 词，倒排索引反过来，是词 → 文档列表。比如有三个菜品：'宫保鸡丁'、'鱼香鸡丝'、'宫保虾仁'，分词后建立倒排索引：'宫保' → [1,3]，'鸡丁' → [1]，'鸡丝' → [2]。搜索'宫保'时直接从索引拿到文档 1 和 3，不需要全表扫描。"

**Q：IK 分词器的 ik_max_word 和 ik_smart 有什么区别？**

> "ik_max_word 做最细粒度切分，比如'中华人民共和国'会切成'中华人民共和国、中华人民、中华、人民共和国、人民、共和国、共和、国'。ik_smart 做最粗粒度切分，只切成'中华人民共和国'。我在索引时用 ik_max_word，保证所有可能的词都被索引到；搜索时用 ik_smart，用户的搜索词不会被过度拆分。"

---

### 【第二层追问】数据同步

**Q：ES 和 MySQL 数据不一致怎么办？**

> "我做了三层保障。第一，MQ Consumer 消费失败会上抛异常，RabbitMQ 自动重新投递；第二，菜品 CRUD 在 Service 层同步写 ES，try-catch 不阻断主流程；第三，也是兜底，我写了一个定时对账任务，每小时跑一次。菜品是全量对比——数据量小，百级——逐条从 ES get 出来和 MySQL 比 status、name、price 这些字段，不一致就覆盖写入。订单因为分了 16 张表，全量代价大，所以只对账最近 24 小时的，从 MySQL 广播查出来，再 multiGet ES，发现缺失或 status 不同就重新构建 OrderDocument 写回去。这样即使 MQ 消费丢了、ES 短暂宕机，最多一小时就能自动修复。"

**Q：对账任务为什么菜品全量、订单只查 24 小时？**

> "菜品没有分片，单表就百来条数据，全量扫描没有压力。订单分了 2 库 16 张表，listRecentOrders 没有带分片键，ShardingSphere 会广播到 16 张表。如果全量查，数据量大且每次都广播 16 片，对数据库压力很大。限制在 24 小时内，一方面数据量可控，另一方面实际上 ES 数据丢失主要发生在写入附近时间窗口——比如 MQ 消费失败、ES 短暂不可用——超过 24 小时还没被发现的概率极低。"

**Q：为什么不用 MySQL 的全文索引？**

> "MySQL 5.7 开始支持全文索引，但对中文的分词能力很弱，需要额外安装插件，且性能远不如 ES。ES 天然支持分布式、支持多种分词器、支持复杂查询（模糊、聚合、高亮），生态更成熟。"

### 【第三层追问】深入问题

**Q：ES 写入失败你选择 try-catch 降级，为什么不用更强的一致性保证？**

> "菜品搜索不是交易链路，短暂搜不到一个菜品不会造成资金损失。如果用强一致（比如分布式事务），写菜品时 ES 挂了就会导致整个 CRUD 失败，影响面反而更大。所以选择可用性优先，最终一致，再加对账任务兜底，最坏情况一小时自动修复。"

**Q：为什么不用 Canal 监听 binlog 同步 ES？**

> "Canal 的优势是业务代码完全不感知 ES，写入入口再多也不怕遗漏。但代价是需要额外部署 Canal Server + Adapter，多一个组件要运维监控。而且我们用了 ShardingSphere 分库分表，binlog 里的物理表名是 `orders_0`、`orders_3` 这些，和逻辑表名不一致，Canal 适配起来有兼容性问题。我们项目写入入口就几个 Service，手动双写完全可控，加上 MQ 异步同步和定时对账兜底，三层保障已经足够。Canal 更适合写入入口分散、团队规模大、无法在每个 Service 都加双写代码的场景。"

---

### 【第四层追问】ES 核心概念（面试高频）

**Q：ES 的索引、类型、文档是什么关系？**

> "类比 MySQL：索引相当于数据库，类型相当于表（ES 7.x 之后废弃了类型，一个索引只有一个默认类型 `_doc`），文档相当于行。一个文档就是一条 JSON 数据。"

**Q：ES 写入数据的流程是什么？**

> "客户端发请求到协调节点，协调节点根据文档 ID 哈希算出属于哪个主分片，转发到主分片所在的节点。主分片写入后同步到副本分片，副本确认后返回客户端。写入时先写 translog（类似 MySQL 的 redo log，保证断电不丢），再写内存 buffer，定期 refresh 到 segment 后才能被搜索到，默认 1 秒 refresh 一次，所以 ES 是近实时搜索，不是实时。"

**Q：ES 怎么实现分布式的？**

> "ES 把一个索引拆成多个分片（shard），每个分片是一个独立的 Lucene 实例，分布在不同节点上。查询时协调节点把请求发到所有相关分片，各分片返回局部结果，协调节点合并排序后返回。这个过程叫 scatter-gather。每个主分片还有副本分片做高可用，主分片挂了副本自动顶上。"

## 模块六：UV/PV 实时统计

### 【主动讲解】30 秒话术

> "我用 Redis 做了 UV/PV 统计。实现方式是在 Spring MVC 里加一个拦截器，对所有用户端请求透明埋点。PV 用 Redis 的 INCR 原子计数，每次请求 +1。UV 用 HyperLogLog，调用 PFADD 把 userId 加进去，天然去重。查询时 PFCOUNT 返回 UV 估算值。"

---

### 【第一层追问】HyperLogLog 原理

**Q：HyperLogLog 为什么能用 12KB 统计亿级基数？**

> "核心思想是用概率估算代替精确计数。对每个元素做哈希，统计哈希值二进制前导零的最大长度。直觉上，出现 n 个前导零的概率是 1/2^n，所以看到的前导零越长，说明不同元素越多。Redis 用 16384 个桶，每个桶记录各自的最大前导零长度，最后取调和平均得到整体估算。每个桶只需要 6 bit（最多 64 个前导零），16384 × 6 bit ≈ 12KB。"

**Q：误差 0.81% 怎么来的？**

> "HyperLogLog 的标准误差公式是 `1.04 / √m`，m 是桶数。Redis 用 16384 个桶，代入就是 `1.04 / √16384 = 1.04 / 128 ≈ 0.0081`，就是 0.81%。桶越多精度越高但内存越大，16384 是精度和内存的平衡点。"

---

### 【第二层追问】方案对比

**Q：为什么不用 Set？**

> "Set 是精确去重，但内存随用户量线性增长。假设 100 万用户，每个 userId 是 Long 型 8 字节，一天的 Set 就要 8MB。而 HyperLogLog 不管多少用户，固定 12KB。对于 UV 这种运营参考数据，0.81% 的误差完全可以接受。"

**Q：为什么不用 Bitmap？**

> "Bitmap 用 userId 做下标，内存取决于最大 userId 的值，不是用户数量。如果 userId 从 1 到 100 万且连续，Bitmap 只要 125KB，比 Set 省。但如果 userId 不连续、值域很大，比如有个用户 userId 是 2 亿，Bitmap 就要分配 25MB，中间全是空洞浪费。HyperLogLog 对 userId 的分布完全不敏感。"

---

### 【第三层追问】工程细节

**Q：为什么用拦截器不用 AOP？**

> "拦截器工作在 Servlet 层，比 Spring AOP 更早执行，不需要依赖 Spring Bean 代理。而且 AOP 需要定义切点表达式匹配 Controller 方法，拦截器直接匹配 URL 路径更直观，配置也更灵活。"

**Q：Redis 挂了怎么办？UV/PV 数据会丢吗？**

> "UV/PV 是非核心链路，拦截器里做了 try-catch 降级，Redis 不可用时跳过统计，打一条 WARN 日志，不影响用户正常请求。数据确实会丢一部分，但 UV/PV 本身就是估算值，短暂丢失对业务决策影响不大。如果要更高可靠性，可以考虑先写本地日志再异步同步，但这个项目规模不需要。"

**Q：key 的过期策略呢？不会无限增长吗？**

> "每天的 key 格式是 `pv:2026-03-14`、`uv:2026-03-14`，可以给 key 设置 TTL，比如保留 90 天的数据，超过的自动过期。也可以在查询接口里做限制，最多查最近 90 天。"

## 模块七：订单超时关闭

### 【主动讲解】30 秒话术

> "订单超时关闭我做了双路径设计。主路径用 Redis 的 Sorted Set，用户下单时 ZADD 把订单写进去，score 是下单时间戳。定时任务每 60 秒用 rangeByScore 查出超过 15 分钟未支付的订单，逐条取消。兜底路径每 5 分钟全库广播扫描数据库，防止 Redis 数据丢失。"

---

### 【第一层追问】为什么用双路径

**Q：为什么不只用数据库扫描？**

> "数据库扫描的问题是订单表分了 16 张表，每次查都要广播到所有分片，QPS 高时对数据库压力大。Redis ZSET 的 rangeByScore 是 O(log N + M) 的操作，内存中完成，不需要碰数据库。"

**Q：那为什么不只用 Redis，还要兜底扫描？**

> "Redis 不是持久化存储，有丢数据的风险。比如 Redis 宕机重启、主从切换丢 key、或者下单时 ZADD 写入失败了。如果只依赖 Redis，这些订单就永远不会被取消了，用户付不了款也退不了。所以用数据库扫描兜底，保证最终一定能关掉。"

**Q：兜底阈值为什么是 20 分钟，比主路径的 15 分钟多 5 分钟？**

> "避免主路径和兜底路径重复处理同一个订单。主路径 15 分钟取消，兜底用 20 分钟，这样正常情况下订单已经被主路径取消了，兜底扫出来时状态已经变了，不会重复操作。多出的 5 分钟刚好等于兜底扫描的间隔周期，给主路径留足处理窗口。"

---

### 【第二层追问】ZSET 细节

**Q：ZSET 里存的是什么？**

> "member 是 `orderId:userId`，score 是下单时间的毫秒时间戳。取消时从 member 里解析出 orderId 去取消订单，取消成功后 ZREM 移除。存 userId 是为了后续如果需要精准路由分片时可以用到。"

**Q：取消失败了怎么办？**

> "catch 异常后不执行 ZREM，这条 member 留在 ZSET 里，下一轮循环会再次扫到并重试。相当于 ZSET 本身就是一个天然的重试队列。如果反复失败，兜底的数据库扫描也会兜住。"

## 模块八：Redis Pipeline 性能优化

### 【主动讲解】30 秒话术

> "我在做 UV/PV 统计时发现了 Redis 调用的性能问题，用 Pipeline 做了优化。写入端拦截器每个请求要执行 INCR 和 PFADD 两条命令，原来是两次网络往返，改成 Pipeline 后合并为一次。查询端更明显，查 30 天的 UV/PV 报表原来要循环 30 天、每天 2 次调用、共 60 次网络往返，改成 Pipeline 后一次往返就拿回全部结果。"

---

### 【第一层追问】Pipeline 原理

**Q：Pipeline 为什么能提升性能？**

> "Redis 本身执行命令很快，瓶颈在网络往返。每次调用都要经历：发请求 → 等响应 → 再发下一个。Pipeline 把多条命令打包一次性发出去，Redis 依次执行后把所有结果一次性返回。省掉的是中间 N-1 次网络等待时间。"

**Q：Pipeline 和事务（MULTI/EXEC）有什么区别？**

> "Pipeline 是客户端的批量优化，只减少网络往返，不保证原子性，中间某条命令失败不影响其他命令。事务（MULTI/EXEC）保证原子性，要么全执行要么全不执行。UV/PV 的场景不需要原子性——PV 少计一次、UV 多计一次都无所谓——所以用 Pipeline 就够了，开销更小。"

---

### 【第二层追问】菜品缓存策略

**Q：菜品缓存是怎么做的？**

> "做了四层：布隆过滤器 → Caffeine L1 → Redis L2 → DB。
>
> 第一层是 Redisson 布隆过滤器，启动时把全量 categoryId 预热进去，误判率 1%。用户请求进来先过布隆过滤器，categoryId 不存在直接返回空，不走后面任何一层，防缓存穿透。
>
> 第二层是 Caffeine 本地缓存，最大 100 条，TTL 60 秒。进程内访问，不走网络，纳秒级响应。
>
> 第三层是 Redis，key 是 `dish_{categoryId}`，TTL 是 30 分钟加 0 到 10 分钟随机偏移。随机偏移是为了防缓存雪崩——如果所有分类缓存同时过期，瞬间大量请求同时打到 DB，DB 扛不住。Redis 命中后会同时回填 Caffeine，下次请求直接 L1 命中。
>
> 都未命中才查 DB，查完同时回填 Redis 和 Caffeine。"

**Q：管理员改了菜品数据，缓存怎么更新？**

> "管理端修改菜品、启停售、删除菜品时，Service 层会主动清除对应分类的缓存 key。用户下次请求时缓存未命中，重新从数据库加载最新数据。TTL 是第二道保障，即使主动清除遗漏了，最多 40 分钟后缓存也会自然过期。"

**Q：缓存击穿怎么处理？**

> "缓存击穿是某个热点 key 过期瞬间大量请求打到数据库。我们的菜品数据是按分类拆 key 的，单个 key 的并发不会特别高。如果真要防，可以用 singleflight 模式，同一个 key 只允许一个请求回源查数据库，其他请求等结果。不过目前这个规模还不需要。"

**Q：缓存清理时你是怎么删 Redis key 的？**

> "之前用的 `KEYS dish_*`，后来发现这是生产大忌——`KEYS` 是 O(N) 全量扫描，执行期间阻塞 Redis 单线程，key 多时会导致所有请求超时。改成了 `SCAN` 迭代游标，每次只返回一小批（count=100），不阻塞主线程，通过游标循环直到扫完全部匹配 key 再批量删除。代价是多次网络往返，但缓存清理是低频的管理端操作，完全可以接受。"

**Q：你用了 Caffeine 做本地缓存，如果部署多个实例，一个节点更新了数据，其他节点的本地缓存怎么办？**

> "这是多实例下本地缓存一致性的经典问题。我的方案是用 Redis Pub/Sub 做广播通知。管理端修改菜品数据时，除了清除本节点的 Caffeine 和 Redis 缓存外，还往一个固定的 Redis Channel（比如 `cache:dish:invalidate`）发一条消息，消息体就是被清除的 key pattern。所有节点启动时都订阅这个 Channel，收到消息后清理自己本地的 Caffeine 缓存。这样写操作发生后，所有节点的本地缓存几乎同时失效，下次请求会从 Redis 或数据库重新加载。"

**Q：Pub/Sub 消息丢了怎么办？**

> "Redis Pub/Sub 是 fire-and-forget 的，如果某个节点恰好断连确实会丢消息。但 Caffeine 本身设了 60 秒 TTL，最坏情况就是某个节点多读了最多 60 秒的旧数据，对外卖场景来说可以接受。如果要更强的一致性，可以把 Pub/Sub 换成 Redis Stream 或者 RocketMQ 广播消费，消息有持久化和 ACK 机制，不会丢失。不过对于菜品这种低频更新的数据，Pub/Sub + TTL 兜底已经够用了。"

## 模块九：下单接口幂等 — 防重复提交

### 【主动讲解】30 秒话术

> "下单接口做了幂等保护，防止用户网络抖动或快速双击导致重复创建订单。方案是 Token 机制：前端在打开下单页时先调 `GET /user/order/token` 获取一个 UUID 令牌，服务端把 `order:token:{userId}:{token}` 存进 Redis，TTL 10 分钟。用户提交时在请求头 `X-Order-Token` 带上这个 token，服务端原子执行 `Redis.delete(key)`，返回 true 说明 key 存在且本次是第一个到达的请求，放行；返回 false 说明 key 不存在（已被消费或伪造），直接返回'请勿重复提交'。"

---

### 【第一层追问】为什么用 delete 而不是 SETNX

**Q：你为什么用 delete 做幂等判断，而不是先 SETNX 再删？**

> "SETNX 是'不存在则写入'，用于加锁场景。我这里反过来——token 由服务端预先写好，客户端拿到后提交时一次性删除。delete 是原子操作，两个并发请求同时删同一个 key，只有一个能拿到 true，另一个得到 false 被拒绝。逻辑更直接，不需要额外的 Lua 脚本或两步操作。"

**Q：为什么 token 绑定 userId，不直接用 token 做 key？**

> "防止用户 A 拿到 token 后传给用户 B 来绕过校验，或者恶意枚举 token。key 里带上 userId，服务端从 JWT 里取 userId 拼接，用户无法伪造别人的 key。"

**Q：token 过期了但用户还没提交怎么办？**

> "TTL 设的 10 分钟，正常下单流程几秒内完成，10 分钟足够了。如果真的超时，delete 返回 false，前端收到'请勿重复提交'的错误，可以提示用户刷新页面重新获取 token 再试。"

## 模块十：WebSocket 订单状态实时推送

### 【主动讲解】30 秒话术

> "用户下单后需要实时知道订单状态变化，比如商家接单、开始配送、已完成。我用 WebSocket 实现了服务端主动推送。用户端打开订单页时，通过 `ws://host/ws/order/{jwt_token}` 建立长连接，服务端校验 JWT 后按 userId 维护 session。商家接单、拒单、派送、完成等 7 个状态变更点，以及物流 MQ 消费端，都会触发 WebSocket 推送，用户端收到 JSON 消息后实时更新页面，不需要轮询。"

**Q：你项目里的 WebSocket 是干什么的？**

> "我用它做订单状态实时推送。用户打开订单页后建立长连接，后端保存这个用户的连接。只要订单状态变化，比如支付成功、商家接单、拒单、配送中、已完成，或者物流 MQ 更新状态，后端就主动推一条消息给前端，前端收到后直接刷新订单状态，不用轮询接口。"

**Q：具体是怎么实现的？**

> "服务端用了 `@ServerEndpoint(\"/ws/order/{token}\")` 暴露 WebSocket 端点。用户连接时把 JWT token 带上，服务端在 `@OnOpen` 里解析 token，拿到 userId 后把 `userId -> Session` 放进 ConcurrentHashMap。后面订单状态变更时，不是直接在业务里发字符串，而是统一走 `OrderStatusNotifier`，封装成 JSON，再调用 `sendToUser(userId, message)` 推送给对应用户。"

---

### 【第一层追问】为什么不用轮询

**Q：为什么不用轮询？WebSocket 比轮询好在哪？**

> "轮询是客户端每隔几秒发一次 HTTP 请求问'有没有新状态'，绝大多数请求返回'没有变化'，浪费带宽和服务端资源。WebSocket 是全双工长连接，服务端有状态变更时主动推过去，没变更时不通信。对于外卖场景，一个订单的状态变更就几次，但轮询间隔内可能发几十次无效请求，WebSocket 的效率高很多。"

**Q：WebSocket 和 SSE（Server-Sent Events）有什么区别？**

> "SSE 是单向的，只能服务端推给客户端，走的是 HTTP 协议。WebSocket 是双向的，走独立的 ws 协议。我们这个场景确实只需要服务端推送，SSE 也能实现。但微信小程序原生支持 WebSocket（`wx.connectSocket`），不支持 SSE，所以选了 WebSocket。"

---

### 【第二层追问】鉴权与安全

**Q：WebSocket 怎么做身份认证？**

> "WebSocket 握手是一个 HTTP Upgrade 请求，但微信小程序的 `wx.connectSocket` 不支持自定义 header。所以我把 JWT token 放在 URL path 里：`ws://host/ws/order/{token}`。服务端在 `@OnOpen` 回调里解析 token，校验通过就把 userId 和 Session 存入 ConcurrentHashMap，校验失败直接关闭连接返回 VIOLATED_POLICY。"

**Q：token 放在 URL 里不安全吧？**

> "确实不如 header 安全，URL 可能被日志记录或浏览器历史缓存。但 WebSocket 连接是长连接，token 只在握手时传一次，不像 HTTP 每次请求都带。而且用的是 wss（TLS 加密），中间人看不到 URL 内容。生产环境如果要更安全，可以先用一次性的短 token 换取 WebSocket 连接权限，握手成功后短 token 立即失效。"

---

### 【第三层追问】连接管理

**Q：用户没有打开 App，WebSocket 推不出去怎么办？**

> "推送是尽力而为的，`sendToUser` 先查 ConcurrentHashMap，session 不存在或已关闭就跳过，不影响主业务。用户下次打开订单页时，页面加载会调 HTTP 接口查最新状态，WebSocket 推送只是优化用户体验让状态更新更实时，不是唯一的状态同步手段。"

**Q：如果部署多实例，WebSocket session 在不同节点怎么办？**

> "目前是单体部署，ConcurrentHashMap 够用。如果要多实例，session 分布在不同节点，需要引入一个广播机制。方案和 Caffeine 多实例一致性类似：状态变更时往 Redis Pub/Sub 发一条消息，所有节点收到后各自检查本地有没有对应用户的 session，有就推。"

---

## 模块十一：付费券购买防超卖

### 【主动讲解】30 秒话术

> "免费券抢购我放在 Redis 里，允许最终一致。付费券要先预留、付款成功再确认，中间不能超卖，也不能出现付了钱库存没扣掉，所以我把预留和账本放在同一个 MySQL 里。库存不用一行数量，改成每件一行，预留用 `SKIP LOCKED` 让并发请求各拿各的行，事务用 RC，避免池子空了补货时被间隙锁挡住。压测时吞吐卡在大约 1000 TPS，CPU 没打满，连接池先满了。定位到是确认在等热点账本行的锁，连接一直不还。后来把同时排队的确认合成一个事务，一次锁、一次扣减、一次提交。单机双热点券的预留加确认，从大约 980 TPS 做到大约 7600 TPS，256 并发 P99 大约 64 毫秒，MySQL 大概 1.6 个核，账本和确认数对得上。"

说完停一下。面试官如果问「和抢券那个 5200 QPS 怎么比」，先把口径说清楚，再讲细节。

### 背景：为什么这条链路不走 Redis

**Q：免费券已经用 Redis 了，付费券为什么还要做一套 MySQL？**

> "免费券抢不到不影响钱，Redis 预扣成功以后可以异步落库，最后对账兜底。付费券和支付绑在一起，下单时要先把库存占住，支付成功再真正扣掉，取消或者超时要把占住的还回去。如果预留在 Redis、账本在 MySQL，支付成功扣账本和清掉预留没法放进同一个事务，就会出现钱扣了库存没扣，或者库存扣了预留还占着。"
>
> "所以预留、确认、账本都在同一个库里。预留发生在开始支付，确认发生在支付成功，这是两个事务，中间隔着支付，不会写成一个大事务把连接占住。"

### 方案：一件一行，确认再扣数量列

**Q：表是怎么设计的？预留和确认各自改哪张表？**

> "可用库存是 `paid_coupon_available_unit`，一件一行。预留是 `paid_coupon_reserved_unit`，也是一件一行。账本是 `paid_coupon_inventory`，每种券一行，上面有 `remaining` 这个数量列。一种券不会把全部库存都铺成行，可用池最多 1000 行，用完再从账本补。"
>
> "预留：`SELECT ... FOR UPDATE SKIP LOCKED` 从可用池拿走若干行，先删可用池，再插入预留表，不改 `remaining`。确认：删掉这笔预留，再把账本的 `remaining` 扣掉。释放只删预留，不改账本，额度可以再补回池子。"
>
> "数量列我试过直接拿来做预留，所有人改同一行，行锁排队。改成一件一行之后，预留锁的是不同的单位行，`SKIP LOCKED` 会跳过别人已经锁住的行。"

**Q：为什么用 RC，不用默认的 RR？**

> "池子被拿空、需要补行的时候，RR 下 `SELECT ... FOR UPDATE SKIP LOCKED` 扫到空范围会加间隙锁，补池的插入插不进去，还可能和预留死锁。RC 对这种锁定读不加同样的间隙锁，补池能插进去。业务写事务都显式设成 RC，不是改全局隔离级别。"

### 困难：加压不涨吞吐，连接先满

**Q：方案做完以后压测看到什么？**

> "场景是两种热点券，每种总量 1000 万，池子 1000，不会被抢光。每个用户预留 A、B 各一张，再确认，算 1 TPS，里面是 2 次 HTTP。闭环并发 16、64、128、256，每档 20 秒，跑两轮。双 1 和连接池 50 没改。"
>
> "原始版本从 16 并发加到 256，吞吐一直在 880 到 1000 TPS 左右，16 并发两轮大约 980 TPS 是当时的峰值。64 并发时应用 CPU 大约 159%，MySQL 大约 119%，也就是一个多核，没打满。连接池 50 个全被借走，还有 14 个线程在等连接。全流程 P99 从 16 并发的大约 40 到 50 毫秒，涨到 128 并发的 360 毫秒以上。"

**Q：连接是怎么被占满的？**

> "我按业务打了标签，用连接池回调记每类请求借了多久、等多久。64 并发下，确认占了业务连接时间的 92%。每笔确认大约 47 毫秒，几乎都在 `paid_coupon_inventory` 上对 `remaining` 那一行做 `SELECT ... FOR UPDATE`。"
>
> "所有人都确认同两种券，就挤在这两行上。事务一开始就把连接借走了，然后在等前一笔提交。双 1 还要刷盘。等锁的时候连接不还，池子就满了。预留不是这个原因，它锁的是不同的单位行。"

### 迭代：热点行还在，但不再每笔锁一次

**Q：你怎么优化的？**

> "先确认不是连接数不够。池子从 50 调到 100，吞吐不升。也不是刷盘到了机器上限，同样双 1 下最小事务的提交能力远高于业务需要的每秒两三千次。"
>
> "热点行一次只能过一个事务，单笔把 SQL 写短，也还是每笔一次加锁、一次提交。所以改成同一时刻排队的确认共用一个事务：批量校验每笔请求，按券把数量加总，一条 `UPDATE` 扣 `remaining`，一次提交再还连接。扣不够或者校验失败，整批回滚，每笔退回原来的单笔路径。预留也按同样的方式合并，少往返。"
>
> "另外扫单位行时，被删掉还没 purge 的记录堆在索引前面，每次从最小 id 扫会放大几十倍，所以记住上次锁到的位置，从那里接着扫，扫不够再回头。池子快空时提前补，避免所有请求一起失败重试。"

### 结果

**Q：优化完数据是多少？CPU 呢？**

> "和原始版本同一套压测、两轮取平均。峰值从 16 并发的大约 979 TPS，到 256 并发的大约 7555 TPS，大约 7.7 倍。单轮最高大约 7617 TPS。64 并发从大约 952 TPS 到大约 5978 TPS。"
>
> "CPU 是 `ps` 的单核百分比，100% 就是 1 个核。优化前峰值那边，应用大约 182%，MySQL 大约 119%。优化后 256 并发，应用大约 202%，MySQL 大约 160%，大概 2 个核和 1.6 个核。64 并发对比更直接：应用从 159% 到 174%，MySQL 从 119% 到 139%，吞吐从 952 到 5978。吞吐涨了大约 6 倍，CPU 只多了零点几个核。"
>
> "延迟和连接：64 并发全流程 P99 从大约 149 和 176 毫秒，降到大约 29 和 20 毫秒。128 并发 P99 从大约 360 毫秒降到几十毫秒。每笔业务占用连接从大约 52 毫秒降到大约 0.48 毫秒，借连接从大约 2.3 次降到大约 0.2 次，因为一批请求共用一次借连接。连接池不再排队。每轮都核对了初始库存减 remaining 等于已确认数，错误数是 0。"

**Q：这 7600 TPS 和抢券的 5200 QPS 能比吗？**

> "不能直接比。抢券是 10 万个请求抢 1 万张，Redis Lua 预扣，大部分人抢不到，QPS 是 HTTP 请求数。这边是库存充足，测的是持续把预留和确认做完，1 TPS 里有 2 次 HTTP，7600 TPS 大约是 1.5 万次 HTTP。一个是抢光，一个是热点库存上的持续事务吞吐。"

**Q：还有什么没做完？**

> "服务、MySQL、Redis 和压测客户端在同一台机器上，重复跑有大约 10% 的波动，没有做长时间稳定性，也没有多机。合并提交只在一个 JVM 里生效，多实例时热点行上还有实例个数那么多的并发事务。扫描起点和提前补池也是单机内存里的提示，错了只会多扫、晚补，不会超卖。"

## 通用防守问题

### Q：这个项目是你自己做的还是跟着教程做的？

> "基础的业务功能，比如用户登录、菜品管理、下单支付，是参考教程搭的。但高并发抢券、付费券购买防超卖、分库分表、Snowflake + 号段 fallback、Outbox 消息一致性、ES 检索和对账、限流降级这些是我自己在项目上扩展和重构的。过程中踩过不少实际问题，比如 ShardingSphere Snowflake ID 不回写实体、Redis ZSet member 同毫秒覆盖导致限流计数偏小、Redis 预占和 DB 落库之间的补偿边界，这些都是自己调试和补齐的。"

### Q：项目的并发量 / 用户量有多大？

> "这是个学习项目，没有真实线上流量。但我做技术选型时是按照一定规模来考虑的，比如分 16 个分片是为了支撑千万级订单、HyperLogLog 是为了应对百万级 UV。我更想展示的是面对这些场景时的技术思考和方案设计能力。"

### Q：你觉得这个项目还有什么可以改进的？

> "有几个点。第一，抢券链路现在已经有死信重放和对账，但还可以把补偿结果接入告警，比如死信回滚数量、DB 补偿数量突增时主动通知。第二，商家端近期订单用 DB + ES 合并解决可见性，但如果后台查询量继续上来，最好单独建 `order_admin_view` 投影表，避免管理端复杂查询影响分片订单表。第三，限流现在是应用内拦截器，如果生产多服务、多入口部署，可以把一部分规则前移到网关层，应用内限流作为第二道保护。"

### Q：你是怎么做技术选型的？举个例子。

> "以订单超时关闭为例。需求是未支付订单 15 分钟后自动取消。候选方案有三个：第一，定时任务扫数据库；第二，RabbitMQ 延迟队列；第三，Redis ZSET。"
>
> "定时任务最简单，但我们分了 16 张表，每次扫描要广播全片，频率高了数据库扛不住，频率低了取消不及时。延迟队列精度高，但 RabbitMQ 的延迟插件需要额外安装，而且消息一旦入队就不好取消（用户主动支付后需要取消延迟消息）。Redis ZSET 用 score 存时间戳，rangeByScore 是 O(log N)，性能好，而且支付成功后 ZREM 就能取消，操作简单。"
>
> "最终选了 Redis ZSET 做主路径，再加数据库扫描做兜底，防止 Redis 丢数据。选型的核心标准是：先满足功能需求，再看实现复杂度和运维成本，最后考虑可靠性兜底。"

### Q：如果让你重新设计这个项目，你会怎么做？

> "有三个地方我会改。第一，商家端查询一开始就单独设计投影表或读模型，不让复杂后台查询直接依赖分片订单表和 ES 最终一致。第二，抢券、订单、ES 同步这些异步链路一开始就统一走 Outbox + MQ + 消费幂等 + 对账，不在不同模块里各自演进一套补偿逻辑。第三，限流规则一开始就配置化并接入监控，把 Redis 主限流命中数、本地 fallback 命中数、降级次数都打出来，这样能更清楚地判断系统是否正在被攻击或者 Redis 是否不稳定。"

---

### Q：项目里用到了很多 Redis，如果 Redis 挂了整个系统会怎样？

> "要分链路看。UV/PV 这类非核心统计，Redis 挂了可以跳过，最多丢一部分统计。缓存查询可以回源 DB，但要注意限流和熔断，不能让流量直接打爆数据库。订单超时关闭有数据库扫描兜底。限流这块不能简单放行，所以我做了风险分级：抢券 Redis 异常直接 fail-closed；下单和登录走本地严格 TokenBucket；普通查询走本地宽松 TokenBucket，并且连续 Redis 异常会进入降级状态。抢券主链路依赖 Redis Lua 做预占，所以 Redis 不可用时直接拒绝抢券请求，保证不会因为降级造成超卖。"

---

### Q：你怎么保证代码质量？

> "三个层面。第一，写代码时遵循一些原则：缓存操作用 SCAN 不用 KEYS、DB 操作带分片键避免广播、幂等校验前置。这些不是凭感觉，而是踩过坑之后形成的 checklist。第二，每个功能写完我会做边界测试，比如优惠券抢购用 JMeter 压 1000 并发验证零超卖，对账任务手动制造 ES 和 DB 不一致再验证修复。第三，关键链路都有兜底机制——Outbox 重试 + 对账、Redis ZSET + 数据库扫描、Caffeine TTL + Redis 主动清除——不依赖单一路径的正确性。"

### Q：你平时怎么学习新技术的？

> "以这个项目为例，ShardingSphere 和 Elasticsearch 之前都没用过。我的方法是先看官方文档理解核心概念和 API，然后直接在项目里用。遇到问题先看错误日志和源码，而不是直接搜。比如 ShardingSphere Snowflake ID 不回写的问题，搜了一圈没人遇到完全一样的情况，最后是 debug 进 ShardingSphere 的 `ShardingInsertStatementRewriteEngine` 源码才搞清楚。我觉得最有效的学习方式就是在真实场景里用，踩坑比看十遍文档记得牢。"
