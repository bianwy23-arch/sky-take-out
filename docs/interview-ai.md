# AI 主题面试文档

## Q：JD 里要求 `AI Native` 能力，我怎么体现？

### 核心理解

> 面试官想看的不是“你会不会用 ChatGPT”，而是你有没有把 AI 纳入日常工程闭环。

重点通常有 4 个：

- 日常开发是否持续使用 AI，而不是偶尔体验
- 是否能说清 AI 在工程任务里的具体作用
- 是否会用 AI 做调试、重构、测试、文档，而不只是代码补全
- 是否知道怎么提问、怎么约束、怎么验证

### 30 秒回答版

> 我现在不是把 AI 当成代码补全工具，而是当成工程协作工具。平时会把它用于问题定位、重构草案、测试样例生成和技术文档沉淀。比如我在排查 ShardingSphere Snowflake ID 不回写实体的问题时，会先把现象、技术栈和约束条件整理给 AI，让它按调用链列出可能原因和排查顺序；然后我再回到源码、日志和 SQL 执行链里逐项验证。对我来说，AI 负责提速，最终判断和验收还是我自己来做。 

### 1 分钟展开版

> 我理解的 `AI Native`，不是说我用过几个工具，而是我已经把 AI 放进了日常开发流程里。现在我比较稳定会用它做四类事：第一是问题定位，比如报错现象梳理、调用链排查顺序、异常原因枚举；第二是重构草案，让它先给出模块拆分或代码整理思路；第三是测试样例生成，比如补充边界 case、异常 case；第四是文档沉淀，比如把方案讨论、排查过程整理成结构化文档。  
> 我不会直接照搬 AI 输出，而是把它当成候选方案生成器。像我项目里排查 ShardingSphere Snowflake ID 不回写实体的问题，就是先让 AI 帮我收敛排查范围，再回到源码、日志和 SQL 执行结果里验证，最后确认是中间件生成主键后 MyBatis 拿不到 `getGeneratedKeys()`，所以改成按 `number + userId` 精确回查订单 ID。这个过程里 AI 是提速工具，不是替我做判断的人。

## Q：Prompt 怎么体现？面试官问我“你会 Prompt 吗”怎么答？

### 核心理解

> Prompt 不是花哨话术，而是给 AI 写任务说明书。

面试里不要答成“我会 prompt engineering”，要答成：

- 我会补足上下文
- 我会加约束，减少泛化回答
- 我会规定输出格式，提升可验证性

### 20 秒回答版

> 我理解 prompt 不是一句神奇咒语，而是把背景、目标、约束和输出格式说清楚。我平时不会只问“帮我看看为什么报错”，而是会把技术栈、现象、已知条件和希望 AI 输出的结构写清楚。这样它给出的结果会更聚焦，也更方便我后续逐项验证。

### 1 分钟展开版

> 我现在用 AI 时，会刻意控制两件事：第一是补足上下文，第二是约束输出格式。因为如果问题问得太泛，AI 很容易给出一堆正确但没用的废话。  
> 所以我一般会把 prompt 拆成几个固定部分：背景、现象、已知信息、目标、约束、希望输出格式。比如排查后端问题时，我会告诉它技术栈是什么、错误现象是什么、我已经验证过哪些条件、希望它按调用链给出排查顺序，并且每个原因都要给出验证点和修复方案。这样 AI 的输出更像一个待验证的排查草案，而不是泛泛而谈的说明文。

### 通用 Prompt 模板

```text
背景：
现象：
已知信息：
目标：
约束：
希望输出格式：
```

### 项目内可举的 Prompt 例子

```text
背景：Spring Boot + MyBatis + ShardingSphere-JDBC
现象：insert 成功，数据库里有记录，但 orders.getId() 为空，下游写 orderDetail 时空指针
已知信息：Mapper 使用了主键回填；逻辑表做了分片；SQL 能成功执行
目标：定位最可能原因
约束：
1. 不要泛泛解释分布式主键原理
2. 按调用链给出排查顺序
3. 每个原因都给出具体验证点
4. 给出修复方案和风险
输出格式：
1. 原因
2. 如何验证
3. 修复方案
4. 风险
```

## Q：面试官问“你如何应对 AI 的幻觉”？

### 20 秒回答版

> 我的原则是“AI 只提假设，不直接当答案”。应对 AI 幻觉，我会先把上下文和约束写清楚，减少它乱补全；然后要求它给出依据、影响范围和验证步骤；最后再用源码、日志、官方文档和运行结果交叉验证。任何关键结论都必须经过代码或数据验证，不能直接照抄。

### 1 分钟展开版

> 我不会把 AI 当成结论机器，而是把它当成候选方案生成器。为了降低幻觉影响，我主要做四件事。  
> 第一，尽量把上下文写清楚，比如技术栈、现象、约束条件和我已经验证过的信息，减少它凭空补全。  
> 第二，要求它输出依据、排查顺序和验证步骤，而不是只给结论。  
> 第三，用源码、日志、官方文档和运行结果交叉验证，代码场景里一定要落到本地调试、测试或者 SQL / 接口结果。  
> 第四，如果发现它开始泛化、编造或者给出不相关建议，我会缩小问题范围，重新提问，只让它回答一个具体子问题。  
> 对我来说，AI 负责提速，最终判断权一定在我这里。

### 一句压缩版

> 我的原则是“AI 只提假设，不直接当答案”。

## Q：你用 AI 做过什么具体工程任务？

### 推荐案例：ShardingSphere Snowflake ID 问题排查

### 30 秒回答版

> 我项目里有一个比较典型的案例：ShardingSphere 生成了 Snowflake 主键，但 insert 成功后 Java 实体里的 id 还是空，导致下游写 orderDetail 和 Outbox 时空指针。我先把现象、技术栈和约束条件整理给 AI，让它按调用链给出排查顺序和可能原因；然后我再去看源码、日志和 SQL 执行链，最后确认是中间件直接生成主键，MyBatis 拿不到 `getGeneratedKeys()`。最后我改成按 `number + userId` 精确回查订单 ID，并做了回归验证。

### 可扩展的四类场景

- 问题定位：报错现象梳理、调用链排查顺序
- 重构草案：类职责拆分、方法抽取建议
- 测试样例：补充边界 case、异常 case、并发 case
- 文档沉淀：把方案设计、问题复盘、对账逻辑整理成结构化说明

## 面试收尾句

> 我现在的使用方式是：先把问题结构化，再让 AI 生成候选方案，最后靠源码、日志、测试和运行结果做验证。AI 帮我提速，但不会替我做工程判断。
