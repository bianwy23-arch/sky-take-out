# 分库分表容量验证 - 面试回答稿

## 一句话版

我对分库分表不只是做了 `2 库 8 表` 的路由设计，还在测试环境做了模拟容量验证。结果是：带 `userId` 分片键的核心查询在数据量从 `20 万` 增长到 `300 万` 时，RT 基本稳定在十几到二十毫秒；而不带分片键、需要 `16` 分片广播的后台查询，RT 从 `88.8ms` 增长到 `272.0ms`、`542.1ms`，最后到 `1591.4ms`。所以后面我专门做了 `number + userId` 精确回查，并考虑让管理端复杂检索走 ES，避免数据库广播查询成为瓶颈。

## 我为什么做这个测试

因为分库分表最容易只停留在“会配规则”，但面试官真正关心的是两件事：

- 你的分片键选得对不对
- 数据量上来后，哪些查询会稳定，哪些查询会恶化

我这个项目里订单表按 `user_id` 分片，所以理论上用户侧围绕 `userId` 的查询应该稳定；但管理端按订单号、手机号、状态、时间范围组合检索，不一定带分片键，就可能退化成跨分片广播查询。我做这个测试，就是为了验证这个判断。

## 我怎么测的

- 分片拓扑：`2 库 x 8 表 = 16` 个物理分片
- 造数方式：直接往物理分片表灌订单、订单明细、Outbox 数据
- 数据档位：`20 万`、`50 万`、`100 万`、`300 万`
- 关注的 4 类查询：
  - 精确单片订单号回查：`number + user_id`
  - 模拟广播订单号回查：只按 `number`
  - 单片用户订单列表：`user_id + status`
  - 模拟 16 分片广播状态查询：只按 `status`
- 指标口径：平均 RT、P95/P99

## 结果怎么理解

### 1. 带分片键的核心查询比较稳定

- `20 万` 订单：精确回查 `16.7ms`，用户订单列表 `17.0ms`
- `50 万` 订单：精确回查 `17.1ms`，用户订单列表 `17.1ms`
- `100 万` 订单：精确回查 `17.0ms`，用户订单列表 `17.7ms`
- `300 万` 订单：精确回查 `18.2ms`，用户订单列表 `19.1ms`

这说明按 `userId` 分片后，用户侧核心查询基本一直是单库单表路由，数据量上涨时性能没有明显恶化。

### 2. 广播查询增长很快

- `20 万` 订单：16 分片广播状态查询 `88.8ms`
- `50 万` 订单：16 分片广播状态查询 `272.0ms`
- `100 万` 订单：16 分片广播状态查询 `542.1ms`
- `300 万` 订单：16 分片广播状态查询 `1591.4ms`

这个趋势很明显，说明后台复杂检索如果不走分片键，随着数据量增长会比单片查询先成为瓶颈。

### 3. 为什么我后面要做精确回查和 ES

基于这个验证，我做了两件事：

- 订单号回查尽量补上 `userId`，走 `number + userId` 精确路由，避免广播
- 管理端复杂检索不长期压数据库广播查询，考虑走 ES 做搜索

## 面试时我会怎么说

“我在这个项目里，分库分表不是只做了 ShardingSphere 配置，还做了模拟容量验证。订单按 `userId` 做 `2 库 8 表` 分片后，我把测试环境的数据量从 `20 万` 逐步拉到 `300 万`，重点观察两类查询：一类是带分片键的用户侧核心查询，比如 `number + userId` 回查订单、`userId + status` 查订单列表；另一类是不带分片键的后台检索，比如只按状态或订单号去查。结果比较明确，带分片键的查询一直稳定在十几到二十毫秒，而 16 分片广播查询从 `88ms` 增长到 `272ms`、`542ms`，到 `300 万` 时已经接近 `1.6s`。所以我后面专门做了 `number + userId` 精确回查，并考虑把管理端复杂检索放到 ES，避免数据库广播查询在数据量上来后先扛不住。” 

## 如果面试官追问“你测的是真实业务量吗”

我会明确区分：

- 这不是线上真实订单量
- 这是测试环境下做的模拟容量验证
- 目的不是证明“我项目真实有百万订单”，而是验证分片键设计和查询模式在数据增长下的表现

## 如果面试官追问“你验证出了什么核心结论”

我会答这三句：

- `userId` 作为分片键，能覆盖用户侧最高频核心查询
- 带分片键的查询在数据增长下比较稳定
- 不带分片键的后台检索会随着数据量增长明显恶化，所以需要精确路由或旁路检索
