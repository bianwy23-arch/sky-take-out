# 面试开场项目介绍

## 30 秒版

> "我做的是一个外卖平台后端，基础功能包括用户下单支付和商家履约处理。在这个项目里，我重点做的不是普通 CRUD，而是围绕几个核心问题做了工程化改造：第一是优惠券抢购高并发防超卖，第二是订单链路的最终一致性，第三是基于 ShardingSphere 的分库分表和分片键治理，第四是 ES 检索、缓存、幂等、订单超时和 WebSocket 这些配套能力。另外我还为 Outbox 派发、ES 对账补偿和订单状态通知这些后台任务设计了独立异步线程池，补了拒绝策略、异常处理、慢任务日志和周期监控。分库分表这块我还做过模拟容量验证，把订单数据从 20 万逐步拉到 300 万，观察单片查询和广播查询在数据增长下的表现。整体上我想解决的是，系统在并发、异步、分片和用户体验上的几个关键问题。"

## 1 分钟版

> "我这个项目是一个外卖平台后端，覆盖用户端下单支付和管理端订单履约。基础业务是在教程框架上搭起来的，但我自己重点改造了四块。"
>
> "第一块是优惠券抢购高并发防超卖。我设计了'快速失败 + Redisson 按 couponId 粒度加锁 + Redis DECR 原子扣减 + 锁外异步持久化'的链路，并做了 Redis 和数据库的一致性补偿。用 JMeter 压了 1000 并发抢 500 张券，最后零超卖，Redis 和 DB 数据一致。"
>
> "第二块是订单链路的一致性。我把它拆成四层：库存本地事务强一致、Outbox + MQ 消息最终一致、物流回调异步消费加状态机校验、ES 定时对账兜底。这样既保证主业务正确，又避免把所有链路都做成重型分布式事务。"
>
> "第三块是分库分表治理。我基于 ShardingSphere 按 userId 做了 2 库 8 表共 16 个分片，并统一把关联表都绑定到同一个分片键上，保证订单事务不跨库。我还在测试环境做了容量验证，把订单量从 20 万逐步拉到 300 万，结果是带分片键的核心查询一直稳定在十几到二十毫秒，而 16 分片广播查询从 88ms 增长到接近 1.6s。过程中我还定位并修复了 Snowflake ID 不回写实体导致的下游空指针问题。"
>
> "第四块是检索与稳定性治理，包括 ES 菜品检索和订单查询、多级缓存、Redis 滑动窗口限流、UV/PV 统计治理、下单幂等、订单超时关闭和 WebSocket 实时推送。这些模块单独看不大，但组合起来后，整个系统的完整性和可用性会明显更好。"
>
> "这里还有一个工程化细节是异步任务治理。我把 Outbox 派发、ES 对账补偿和订单状态通知放到独立异步线程池里执行，配置了拒绝策略、异常处理、慢任务日志和周期巡检，避免后台任务堆积影响主业务线程，也方便定位派发慢、对账堆积或通知异常这类问题。"

## 简历一句话 -> 20 秒展开

### 优惠券抢购高并发防超卖

**简历一句话**

> "针对优惠券抢购场景下的超卖与 Redis/DB 不一致问题，设计'快速失败 + Redisson 按 couponId 粒度加锁 + Redis DECR 原子扣减 + 锁外异步持久化'链路，并增加对账补偿。"

**20 秒展开**

> "这块我主要解决两个问题：第一是高并发下不能超卖，第二是锁外 DB 落库失败后不能长期不一致。所以我把最核心的竞争逻辑放在 Redis 和分布式锁里完成，DB 放到锁外异步持久化，再补上重试和定时对账，最后压测验证了 1000 并发下零超卖。"

### 订单链路最终一致性

**简历一句话**

> "针对订单状态变更、MQ 重复投递和 ES 异步同步易产生的数据不一致问题，构建'库存事务强一致 + Outbox 最终一致 + 物流 MQ 状态机校验 + ES 定时对账'四层方案。"

**20 秒展开**

> "这块我没有直接上分布式事务，而是按风险分层。库存放本地事务里保证强一致，跨组件同步用 Outbox + MQ 做最终一致，Consumer 端再用消费日志表做幂等，最后 ES 用定时对账兜底。这样既保证主业务正确，也避免了方案过重。"

### 分库分表与分片键治理

**简历一句话**

> "针对订单数据增长后的路由与事务扩展问题，基于 ShardingSphere-JDBC 按 user_id 拆分为 2 库 x 8 表共 16 个分片，并统一关联表分片键，保证订单链路事务不跨库。"

**20 秒展开**

> "我在这里做的重点不是把表分掉，而是统一全链路分片键。订单、明细、支付、Outbox 都绑定 userId，这样一个订单事务始终落在同一分片里。我还做了模拟容量验证，把订单量从 20 万拉到 300 万，带分片键的单片查询基本一直稳定在十几到二十毫秒，而 16 分片广播查询增长到了 1.5 秒级。过程中我还踩到 Snowflake ID 不回写实体的坑，最后通过 `number + userId` 精确回查把问题修掉了。"

### 检索与稳定性治理

**简历一句话**

> "围绕高频查询与热点接口访问，使用 ES + IK 实现菜品全文检索和订单条件查询，构建'布隆过滤器 + Caffeine + Redis + DB'多级缓存链路；并实现 Redis 滑动窗口限流、UV/PV 统计治理、下单幂等、订单超时双路径兜底与 WebSocket 实时推送。"

**20 秒展开**

> "这一块我把它当成主链路之外的稳定性治理能力。ES 解决搜索和复杂查询压力，多级缓存降低数据库回源，滑动窗口限流保护热点接口，UV/PV 统计补充访问分析，幂等和订单超时保证正确性，WebSocket 提升状态反馈实时性。单个点不算特别大，但组合起来后系统完整性会明显更好。"

### 异步线程池与后台任务治理

**简历一句话**

> "为 Outbox 派发、ES 对账补偿和订单状态通知任务设计独立异步线程池，补充拒绝策略、异常处理、慢任务日志与周期监控，提升后台任务隔离性、查询稳定性与链路可观测性。"

**20 秒展开**

> "这块主要是为后台异步任务做隔离。我没有让 Outbox 派发、ES 对账、WebSocket 通知这些任务混用默认线程池，而是单独配了一个 `8/16/500` 的线程池，统一承接这类非实时后台任务。在线程池里补了拒绝策略、异常兜底、超过 1 秒的慢任务日志和每分钟一次的运行状态巡检；任务自身再用 `AtomicBoolean` 防止上一轮没跑完下一轮又进来。这样做之后，后台补偿任务不会随便挤占主业务线程，出问题时也更容易从日志里定位到是派发慢、对账堆积，还是通知链路异常。"

**参数口径**

> "线程池参数是 core=8、max=16、queue=500、keepAlive=60s。这个池主要跑 I/O 型后台任务，比如 MQ 派发、ES 对账和 WebSocket 通知，所以线程数可以比 CPU 核数略高，但不能无限放大。8 个核心线程保证常态处理能力，16 个最大线程应对短时突发，500 的队列用来削峰；如果队列满了就走 `CallerRunsPolicy` 反压，配合慢任务日志和每分钟巡检再判断是否需要继续调参。"

## 20 秒展开口语版

### 优惠券抢购高并发防超卖

> "这块我主要做的是优惠券高并发防超卖。思路是先用 Redis 做快速失败，没库存的请求直接挡掉；真正进入竞争区后，再按 `couponId` 加 Redisson 分布式锁，在锁里完成扣库存和用户去重。数据库写入放到锁外异步做，再补重试和对账，把性能和一致性一起兼顾。"

### 订单链路最终一致性

> "订单一致性这块，我没有直接上分布式事务，而是分层处理。库存这类核心数据放本地事务里保证强一致，跨系统同步靠 Outbox + MQ 做最终一致，消费端再用消费日志表做幂等，ES 不一致就靠定时对账兜底。这样方案比较稳，也不会太重。"

### 分库分表与分片键治理

> "分库分表这块，我重点做的不是单纯把表拆掉，而是统一分片键。订单、明细、支付、Outbox 都带 `userId`，这样一个订单事务基本都能落在同一个分片里，避免跨库。我还做过一轮模拟容量验证，把订单量从 20 万、50 万、100 万一路拉到 300 万，结果是带分片键的查询一直稳定在十几到二十毫秒，而后台这种 16 分片广播检索已经涨到 1.6 秒左右。过程中我还排查了 Snowflake ID 不回写实体的问题，最后通过 `number + userId` 精确回查把这个坑补掉了。"

### 检索与稳定性治理

> "这一块我一般打包讲。前面是查询能力，用 ES 做菜品全文检索和订单条件查询，再配合布隆过滤器、Caffeine 和 Redis 做多级缓存；后面是稳定性治理，包括 Redis 滑动窗口限流、UV/PV 统计、下单幂等、订单超时双路径兜底和 WebSocket 推送。核心思路就是把查询性能、热点保护和链路正确性一起补齐。"

## 1 分钟深挖版

### 优惠券抢购

> "优惠券抢购这块，我主要想解决两个问题：第一是高并发下不能超卖，第二是 Redis 和数据库不能长期不一致。我的做法是先用 Redis 做无锁快速校验，已售罄请求直接挡掉；真正进入临界区后，用 Redisson 按 `couponId` 粒度加分布式锁，锁内只做三件事：判断用户是否已领、Redis `DECR` 扣库存、记录已领取用户。这样把最核心的竞争逻辑收敛在 Redis 里，执行很快。数据库持久化我放到锁外异步做，避免持锁时间过长。为了防止锁外落库失败，我又补了两层兜底：指数退避重试和定时对账任务。最后我用 JMeter 做了 1000 并发抢 500 张券的压测，结果是零超卖，Redis 和 DB 数据一致。"

### 订单一致性

> "订单链路我没有硬上分布式事务，而是按风险拆成四层。第一层是库存强一致，下单预占、支付确认、取消释放都放在本地事务里，用乐观锁和重试保证不超卖。第二层是消息最终一致，订单状态变更和 Outbox 消息同事务提交，再由 Scheduler 扫描投递 MQ，避免直接双写 MQ 带来的丢消息问题。第三层是消费端幂等，Consumer 先写消费日志表，靠唯一键保证同一事件只处理一次。第四层是 ES 对账兜底，菜品做全量比对，订单只对账最近 24 小时，自动修复异步链路失败带来的索引不一致。这样做的取舍是：核心交易链路本地强一致，跨组件靠异步和补偿闭环，复杂度比 Seata 这类重型方案低。"

### 分库分表

> "分库分表这块，我是基于 ShardingSphere-JDBC 按 `user_id` 做了 2 库 8 表共 16 个分片。我的重点不只是把表分掉，而是做全链路分片键治理：订单、明细、支付、Outbox 都统一带 `userId`，保证一个订单事务始终落在同一分片，不跨库。我还专门做了模拟容量验证，把订单量从 20 万逐步拉到 300 万，结果是带 `userId` 的单片核心查询一直稳定在十几到二十毫秒，而不带分片键的 16 分片广播查询从 88ms 增长到 272ms、542ms，最后到 300 万时接近 1.6s。这也验证了为什么后面要做 `number + userId` 精确回查和 ES 避免广播查询。这里我还踩到过一个比较典型的坑，就是 ShardingSphere Snowflake ID 不会回写到 Java 实体，导致 insert 成功了，但 `orders.getId()` 还是 null，下游写 orderDetail 和 Outbox 直接空指针。后来我定位到是中间件层直接把 ID 拼进 SQL，MyBatis 的 `getGeneratedKeys()` 根本拿不到。我最后改成按 `number + userId` 精确回查订单 ID，既解决了空指针，又避免了广播查询。这个问题很能体现我对中间件行为和分片路由的理解。"

### 检索与稳定性治理

> "稳定性治理这块我一般会打包讲。首先是 ES，我用 IK 分词做菜品全文检索，并把管理端订单条件查询也迁移到 ES，减少复杂条件下的数据库广播查询。其次是缓存，我做了布隆过滤器 + Caffeine + Redis + DB 的多级缓存，解决穿透、雪崩和本地命中率问题。然后是热点保护和链路治理，我补了 Redis 滑动窗口限流、UV/PV 统计与 TTL 治理、下单 Token 幂等、订单超时关闭双路径兜底，以及 WebSocket 订单状态实时推送。我的思路不是把这些点拆得很散，而是把它们都当成主业务之外的配套能力：检索提升查询体验，缓存降低数据库压力，限流保护热点流量，幂等和超时处理保证正确性，WebSocket 提升状态反馈的实时性。"
