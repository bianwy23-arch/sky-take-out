# 付费券预留：按 Shopify 连接瓶颈思路在 main 上复测（单位行 Claim）

测量日期 2026-09-24。本地 `main` 工作区。参考：[Shopify: connections, not CPU](https://shopify.engineering/scaling-inventory-reservations)。

口径与上一轮相同：每轮新建两种热点券，库存各 1,000 万，可用池 1,000；一笔业务 = Reserve A+B 各 1 张再 Claim；闭环 16/64/128/256，每档 20 秒，两轮（第二轮版本顺序反转）；启动后空闲 45 秒；双 1 持久化与连接池 50 未改。全部轮次 `correct=true`，HTTP 与业务错误为 0。

- v0：上一轮原始事务（Claim 对 `paid_coupon_inventory` 做 `SELECT ... FOR UPDATE` 再扣 `remaining`）。
- v9：本轮。Claim 只把预留单位插入 `paid_coupon_sold_unit`，不锁账本行；保留合并提交、扫描提示、低水位补池、对账批量化；快照不再每次 `COUNT(sold)`；付费券路径不再走限流/UVPV 的 Redis 邻居。

## 正式矩阵（两轮加权）

| 指标 | v0 原始 | v9 本轮 | v0 → v9 |
|---|---:|---:|---:|
| 峰值 TPS（最优档两轮均值） | 1,016（16 并发） | 7,272（256 并发） | 7.2 倍 |
| 64 并发 TPS | 897 | 6,227 | 6.9 倍 |
| 128 并发 TPS | 882 | 6,994 | 7.9 倍 |
| 256 并发 TPS | 896 | 7,272 | 8.1 倍 |
| 64 并发全流程 P99 | 212 / 273ms | 24 / 25ms | 约 -90% |
| 128 并发全流程 P99 | 356 / 432ms | 52 / 52ms | 约 -86% |
| 64 并发每笔连接占用 | 55.5ms | 0.47ms | -99% |
| 64 并发借连接次数 | 2.28 | 0.20 | -91% |
| 128 并发取连接等待 | 34.8ms | 0.38ms | -99% |

单轮峰值：v9、256 并发 **7,423 TPS**（约 14,846 HTTP 请求/秒）。连接池 `maxPending=0`，活跃连接 ≤5。上一轮无库 HTTP 上限约 7,700～7,900 循环/秒，本轮峰值约为该上限的 94%。

v0 从 16 到 256 吞吐锁在 880～1,040 TPS；64 并发连接池打满 50、排队 14。归因：Claim 占业务连接时间 92%，`lockByCouponIds` 约 47ms。

## 本轮排查

1. 先跑再看连接，不先改库参数。v0 现象与文章一致：加压不涨、CPU 不高、线程在等连接。
2. 根因是项目补全的 `remaining` 行，不是 Shopify 公开的单位池。Claim 改为只移动本请求的 reserved → sold。
3. 中间态（只改账本、仍每次 `COUNT(sold)`、仍走 Redis 限流）64 并发约 3,615 TPS，P99 变差；`insertSold` 占连接时间一半，快照随已售行变多变慢。
4. 快照用 JVM 已售计数，只在未知时 COUNT；付费券路径去掉对吞吐无贡献的限流/UVPV Redis 往返。之后 256 并发贴到 HTTP 链路上限附近，连接不再排队。

局限：单机混部，约 ±10% 波动；已售计数是单 JVM 视图；未做多小时/多机压测。不要和简历里 Redis 抢券的 5,200 QPS 直接比较。
